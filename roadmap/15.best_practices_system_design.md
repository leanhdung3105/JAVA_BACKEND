## 1. Clean Code Principles

> **🔍 WHAT:** Clean Code là tập hợp nguyên tắc và thực hành để viết code dễ đọc, dễ hiểu và dễ bảo trì – code mà developer khác (hoặc bạn sau 6 tháng) có thể hiểu ngay mà không cần giải thích.
>
> **💡 WHY:** Code được đọc nhiều hơn viết (tỷ lệ 10:1). Code khó đọc = khó debug, khó thêm tính năng, tốn thời gian onboard developer mới, dẫn đến technical debt tốn kém để xử lý.
>
> **⚙️ HOW:** Đặt tên biết mô tả ý nghĩa, function nhỏ làm đúng 1 việc, comment giải thích WHY (không phải WHAT – code đã nói rõ WHAT rồi), tránh magic number, fail fast với validation sớm.
>
> **📍 WHEN/WHERE:** Áp dụng mọi lúc khi viết code – không phải chỉ khi "có thời gian refactor". Code review là nơi enforce clean code standards. Định nghĩa coding convention cho team và maintain bằng Checkstyle/SonarQube.

```java
// ❌ Bad code
public List<User> get(int t, boolean a) {
    List<User> r = new ArrayList<>();
    for (User u : repo.findAll()) {
        if (u.getType() == t && u.isActive() == a) r.add(u);
    }
    return r;
}

// ✅ Clean code
public List<User> findActiveUsersByType(UserType userType) {
    return userRepository.findByTypeAndActiveTrue(userType);
    // Không comment "tìm user active theo type" – tên hàm đã nói rõ
}

// ❌ Magic number
if (user.getAge() > 18) { /* ... */ }

// ✅ Named constant
private static final int MINIMUM_AGE = 18;
if (user.getAge() > MINIMUM_AGE) { /* ... */ }

// ❌ Nested if hell
public String process(Order order) {
    if (order != null) {
        if (order.getStatus() == PENDING) {
            if (order.getTotal() > 0) {
                return "Process...";
            }
        }
    }
    return null;
}

// ✅ Early return (Guard Clause)
public String process(Order order) {
    if (order == null) return null;
    if (order.getStatus() != PENDING) return null;
    if (order.getTotal() <= 0) return null;
    return "Process...";
}
```

> **📝 Giải thích chi tiết sự khác biệt:**
> * **Ví dụ 1 (Đặt tên & Logic)**:
>   * `Bad code`: Tên hàm `get`, tên biến `t`, `a`, `r` vô cùng tối nghĩa, bắt buộc người đọc phải phân tích từng dòng mới hiểu hàm làm gì. Việc load toàn bộ DB lên RAM (`repo.findAll()`) rồi duyệt vòng lặp thủ công sẽ làm sập RAM của hệ thống khi DB lớn.
>   * `Clean code`: Tên hàm `findActiveUsersByType` tự giải thích nghiệp vụ (Self-documenting code). Kiểu enum `UserType` thay thế cho kiểu số nguyên `int t` giúp code cực kỳ tường minh. Giao phó việc lọc dữ liệu cho database xử lý (`findByTypeAndActiveTrue`) giúp tối ưu hiệu năng triệt để.
> * **Ví dụ 2 (Magic Number)**:
>   * Số `18` được gọi là **Magic Number** (con số vô danh kỳ bí). Nếu không có constant `MINIMUM_AGE`, người đọc sau này sẽ không hiểu số 18 đại diện cho điều gì (tuổi đi học, tuổi trưởng thành hay số lượng gì khác). Đặt hằng số tĩnh giúp dễ sửa đổi giá trị này ở một nơi duy nhất cho toàn bộ hệ thống.
> * **Ví dụ 3 (Nested If vs Guard Clause)**:
>   * `Nested if hell` (Địa ngục if lồng nhau): Viết code lồng nhiều tầng `if` làm tăng độ phức tạp thuật toán (Cyclomatic Complexity), làm code bị đẩy thụt lề sâu về bên phải, cực kỳ mỏi mắt khi đọc.
>   * `Early return / Guard Clause` (Bảo vệ đầu vào): Nguyên tắc "Fail Fast" - thực hiện kiểm tra kiểm soát lỗi ngay dòng đầu và trả kết quả sớm. Luồng code chính được kéo thẳng hàng, vô cùng sạch đẹp và giảm thiểu sai sót.

## 2. Design Patterns quan trọng

> **🔍 WHAT:** Design Patterns là các giải pháp được đặt tên và chuẩn hóa cho các bài toán thiết kế phần mềm thường gặp – được tổng hợp bởi GoF (Gang of Four) chia thành Creational, Structural, Behavioral.
>
> **💡 WHY:** Patterns cung cấp vocabulary chung – nói "dùng Strategy Pattern" thay vì giải thích dài dòng cách implement. Đã được chứng minh hoạt động tốt trong thực tế, giúp code extensible và maintainable.
>
> **⚙️ HOW:** Học patterns bằng cách nhận biết vấn đề chúng giải quyết, không phải nhớ code. Spring Framework sử dụng rất nhiều patterns: Singleton (Bean), Proxy (AOP), Template Method (JdbcTemplate), Factory (ApplicationContext).
>
> **📍 WHEN/WHERE:** Builder – tạo object phức tạp. Strategy – thay đổi algorithm runtime. Observer – event handling. Factory – tạo object mà không cần biết class cụ thể. Repository – data access abstraction.

```java
// Builder Pattern – tạo object phức tạp an toàn
Email email = Email.builder()
    .to("user@example.com")
    .subject("Xác nhận đơn hàng")
    .body("Đơn hàng #123 đã được xác nhận")
    .attachments(List.of(invoice))
    .priority(HIGH)
    .build();

// Strategy Pattern – swap algorithm runtime
public interface PaymentStrategy {
    PaymentResult process(BigDecimal amount);
}

@Component public class CreditCardStrategy implements PaymentStrategy { /* ... */ }
@Component public class MomoStrategy implements PaymentStrategy { /* ... */ }
@Component public class BankTransferStrategy implements PaymentStrategy { /* ... */ }

@Service @RequiredArgsConstructor
public class PaymentService {
    private final Map<String, PaymentStrategy> strategies; // Spring inject Map<name, bean>

    public PaymentResult processPayment(String method, BigDecimal amount) {
        PaymentStrategy strategy = strategies.get(method + "Strategy");
        if (strategy == null) throw new UnsupportedPaymentMethodException(method);
        return strategy.process(amount); // dễ thêm payment method mới không sửa code này
    }
}

// Decorator Pattern – AOP cách manual
public class LoggingUserService implements UserService {
    private final UserService delegate;

    @Override
    public UserResponse createUser(CreateUserRequest request) {
        log.info("Creating user: {}", request.getEmail());
        UserResponse result = delegate.createUser(request); // gọi actual service
        log.info("Created user with id: {}", result.getId());
        return result;
    }
}
```

> **📝 Giải thích chi tiết code Design Patterns:**
> * **Builder Pattern**: Giải quyết vấn đề "Telescoping Constructor" (Constructor quá nhiều tham số dẫn đến dễ truyền nhầm thứ tự). Cú pháp Chaining giúp tạo đối tượng cực kỳ sạch sẽ, rõ nghĩa và hỗ trợ kiểm soát tính hợp lệ của thuộc tính trước khi gọi `.build()`.
> * **Strategy Pattern (kết hợp với Spring DI Container)**:
>   * `private final Map<String, PaymentStrategy> strategies`: Một kỹ thuật siêu kinh điển! Spring Boot sẽ tự động quét và tiêm (inject) toàn bộ các class implement `PaymentStrategy` vào `Map` này với Key là tên class viết thường dạng camelCase (như `"momoStrategy"`, `"creditCardStrategy"`).
>   * Khi client truyền lên phương thức `"momo"`, hàm `strategies.get` sẽ tự động lấy ra đúng Bean `MomoStrategy` tương ứng để xử lý. Khi cần thêm một phương thức thanh toán mới (như ZaloPay), bạn **chỉ cần tạo một class mới** `ZaloPayStrategy implements PaymentStrategy` có gắn cờ `@Component` mà hoàn toàn **không cần sửa đổi bất kỳ một dòng code nào** trong class `PaymentService` (Tuyệt đối tuân thủ nguyên lý O - Open/Closed trong SOLID).
> * **Decorator Pattern**: Cho phép ta thêm các hành vi phụ trợ (như ghi log, tính thời gian chạy, bắt lỗi) vào một đối tượng đang có mà không làm thay đổi cấu trúc cốt lõi của đối tượng đó. Lớp `LoggingUserService` bọc ngoài đối tượng `delegate` thật để ghi nhận nhật ký trước và sau khi gọi dịch vụ thực tế.

## 3. API Design Best Practices

> **🔍 WHAT:** API Design Best Practices là tập hợp quy ước về versioning (v1, v2), naming, error format, rate limiting, authentication, backward compatibility giúp API dễ dùng và bền vững theo thời gian.
>
> **💡 WHY:** API là contract với consumer (frontend, mobile, third-party). Breaking API mà không versioning phá vỡ mọi client đang dùng. Good API design giảm thời gian integration và hỗ trợ.
>
> **⚙️ HOW:** Versioning qua URL path (`/api/v1`). Idempotent design cho PUT/DELETE. Rate limiting để bảo vệ server. Pagination cho mọi list response. Consistent error format. Deprecation warning trước khi xóa endpoint.
>
> **📍 WHEN/WHERE:** Thiết kế API trước khi implement – API contract với team frontend. Khi thay đổi API (thêm field bắt buộc, đổi response format) luôn cần version mới để backward compatible.

```
✅ API Design Checklist

Naming:
├── URI là danh từ số nhiều: /users, /orders, /products
├── Không dùng verb trong URI: GET /users (không phải GET /getUsers)
├── Dùng hyphens, không underscore: /order-items, không /order_items
└── Filter qua query param: GET /users?role=ADMIN&active=true

Versioning:
├── URL versioning: /api/v1/users
└── Header versioning: Accept: application/vnd.myapp.v1+json

Response:
├── Pagination mọi list: { data: [...], totalItems, totalPages, currentPage }
├── Consistent error format: { status, error, message, timestamp, fieldErrors }
└── Use HATEOAS khi API public: { data: {...}, links: { self, next, prev } }

Security:
├── HTTPS only (no HTTP in production)
├── Rate limiting: 100 req/min/user
├── JWT expiry ngắn: 15-60 phút
└── Validate và sanitize mọi input
```

## 4. Performance Optimization

> **🔍 WHAT:** Performance optimization là các kỹ thuật tăng throughput, giảm latency và resource usage: database query optimization, caching, connection pooling, async processing, JVM tuning.
>
> **💡 WHY:** Ứng dụng chậm làm mất user (53% user bỏ nếu load > 3s). Tối ưu giúp xử lý nhiều request hơn với cùng hardware, giảm chi phí cloud, cải thiện user experience.
>
> **⚙️ HOW:** Đo trước khi tối ưu (profiling, APM). Bottleneck thường ở DB (N+1, missing index, full table scan) và network (không cache, gọi external API nhiều lần). JVM GC tuning, connection pool sizing.
>
> **📍 WHEN/WHERE:** Load testing sau tính năng mới (k6, JMeter). Profiling trong staging environment. DB slow query log để tìm query chậm. Actuator metrics để monitor JVM health trong production.

```java
// ✅ Async processing với @Async
@Service
public class ReportService {
    @Async("taskExecutor")  // chạy trong thread pool riêng
    public CompletableFuture<Report> generateReport(Long userId) {
        // heavy computation – không block request thread
        Report report = buildReport(userId);
        return CompletableFuture.completedFuture(report);
    }
}

// Gọi nhiều service song song
public DashboardData getDashboard(Long userId) {
    CompletableFuture<UserResponse> userFuture = userService.getUserAsync(userId);
    CompletableFuture<List<Order>> ordersFuture = orderService.getRecentOrdersAsync(userId);
    CompletableFuture<BigDecimal> balanceFuture = walletService.getBalanceAsync(userId);

    CompletableFuture.allOf(userFuture, ordersFuture, balanceFuture).join();
    // 3 DB calls song song thay vì tuần tự
    return new DashboardData(userFuture.get(), ordersFuture.get(), balanceFuture.get());
}

// DB: Pagination đúng cách
@Query("SELECT p FROM Product p ORDER BY p.createdAt DESC")
Page<Product> findAllWithPagination(Pageable pageable);
```

> **📝 Giải thích chi tiết code Tối ưu hiệu năng:**
> * `@Async("taskExecutor")`: Rút ngắn thời gian tải phản hồi API. Các công việc tính toán nặng nhọc (như xuất báo cáo Excel, PDF) sẽ được Spring đẩy sang chạy ở một Thread Pool riêng có tên `taskExecutor`, giúp giải phóng ngay lập tức Thread HTTP chính để phản hồi nhanh về cho client.
> * `CompletableFuture.allOf(...)`: Kỹ thuật chạy đa nhiệm song song. Thay vì ứng dụng phải chờ tuần tự: gọi User (mất 1s) -> gọi Order (mất 1s) -> gọi Wallet (mất 1s) mất tổng cộng 3 giây. Kỹ thuật này kích hoạt cả 3 tiến trình gọi DB/API chạy **đồng thời cùng lúc**. Tổng thời gian xử lý của API lúc này giảm xuống chỉ còn bằng thời gian của tiến trình chạy lâu nhất (~1 giây), nâng hiệu suất phản hồi lên gấp 3 lần.
> * `findAllWithPagination`: **Bắt buộc phân trang ở mức database**. Tuyệt đối không dùng `findAll()` để nạp toàn bộ hàng triệu dữ liệu từ DB lên RAM của Java rồi lọc qua Java Stream API (lỗi tràn bộ nhớ Out of Memory). Bắt buộc sử dụng `Pageable` để database tự động sử dụng từ khóa `LIMIT` và `OFFSET` để chỉ lấy đúng phân khúc dữ liệu cần hiển thị lên RAM.

## 5. Security Best Practices

> **🔍 WHAT:** Security best practices là tập hợp nguyên tắc bảo vệ ứng dụng khỏi các attack vector phổ biến: SQL injection, XSS, CSRF, broken authentication, insecure direct object reference, sensitive data exposure.
>
> **💡 WHY:** Security breach có thể destroy reputation, tốn kém về pháp lý (GDPR, PCI DSS), mất dữ liệu user. OWASP Top 10 là danh sách lỗ hổng phổ biến nhất – mỗi developer phải biết và phòng tránh.
>
> **⚙️ HOW:** Dùng PreparedStatement/JPA (không raw SQL với string concat), validate input, encrypt sensitive data, không log sensitive info, principle of least privilege, dependency scanning (OWASP Dependency Check).
>
> **📍 WHEN/WHERE:** Security là concern xuyên suốt – từ thiết kế đến code đến deployment. Security review trong PR checklist. Penetration testing trước go-live. Bug bounty program cho production app.

```java
// 1. SQL Injection Prevention – dùng PreparedStatement/JPA (không string concat)
// ❌ KHÔNG BAO GIỜ: "SELECT * FROM users WHERE email = '" + email + "'"
// ✅ JPA tự handle: userRepository.findByEmail(email)

// 2. Không log sensitive data
// ❌ log.info("User login: email={}, password={}", email, password);
// ✅ log.info("User login attempt: email={}", email);

// 3. Mã hóa password với BCrypt
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12); // cost factor 12
}

// 4. Environment variables cho secrets
@Value("${app.jwt.secret}")
private String jwtSecret; // không hardcode "my-secret-key"

// 5. Input validation (prevent XSS)
@NotBlank
@Size(max = 255)
@Pattern(regexp = "^[a-zA-Z0-9.@_-]+$") // whitelist characters
private String username;

// 6. IDOR Prevention – kiểm tra ownership
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id, @AuthenticationPrincipal User user) {
    Order order = orderRepository.findById(id).orElseThrow();
    if (!order.getUserId().equals(user.getId()) && !user.isAdmin()) {
        throw new AccessDeniedException("Không có quyền xem đơn hàng này");
    }
    return toResponse(order);
}
```

> **📝 Giải thích chi tiết các nguyên tắc bảo mật:**
> * `BCryptPasswordEncoder(12)`: Đặt độ phức tạp (cost factor) của thuật toán băm mật khẩu là 12. Giúp cân bằng hoàn hảo giữa hiệu năng của máy chủ và độ an toàn mật khẩu chống lại các cuộc tấn công dò mật khẩu dạng vét cạn (Brute-force).
> * `IDOR Prevention (Insecure Direct Object Reference)`: Lỗ hổng kiểm soát truy cập trực tiếp đối tượng. Lỗi xảy ra nếu lập trình viên chỉ viết query lấy đơn hàng `orderRepository.findById(id)` rồi trả về thẳng cho client, dẫn đến việc user A chỉ cần thay đổi số ID trên URL thành ID đơn hàng của user B là xem trộm được toàn bộ thông tin nhạy cảm. Đoạn code bảo mật thực hiện kiểm tra chặt chẽ: Chỉ cho phép người sở hữu đơn hàng hoặc tài khoản Admin có quyền xem thông tin.

## 6. System Design Concepts

> **🔍 WHAT:** System Design là kỹ năng thiết kế kiến trúc hệ thống có thể scale đến hàng triệu user – load balancing, horizontal scaling, database sharding, CDN, caching strategy, CAP theorem.
>
> **💡 WHY:** Phỏng vấn Senior/Staff level luôn có system design round. Thực tế, thiết kế sai architecture từ đầu rất tốn kém để refactor. Hiểu trade-off giúp đưa ra quyết định đúng cho từng context.
>
> **⚙️ HOW:** Học framework: Clarify requirements → Estimate scale → Design high-level → Detail → Identify bottlenecks → Optimize. Biết khi nào dùng SQL vs NoSQL, cache-aside vs write-through, sync vs async.
>
> **📍 WHEN/WHERE:** System design interview. Khi team quyết định kiến trúc mới. Khi cần scale system (traffic tăng 10x). Planning cho new feature có impact lớn đến performance.

```
Typical Web Application Architecture (Scalable)

User → CDN (static assets)
     → Load Balancer (Nginx/AWS ALB)
          ↓
     API Servers (multiple instances) ← Auto Scaling
          ↓                    ↑
     Cache Layer (Redis)   Message Queue (RabbitMQ/Kafka)
          ↓                    ↓
     Primary DB ← Replica   Workers (background jobs)
     (Read replica for heavy read)
          ↓
     Monitoring (Prometheus/Grafana/ELK)
```

```
CAP Theorem – chỉ đảm bảo được 2/3:
├── Consistency  – mọi read nhận được write mới nhất
├── Availability – mọi request đều nhận response
└── Partition Tolerance – hệ thống tiếp tục khi network partition

Databases:
├── MySQL/PostgreSQL → CP (Consistency + Partition Tolerance)
├── Cassandra → AP (Availability + Partition Tolerance)
└── MongoDB → CP (configurable)

Khi nào dùng NoSQL?
✅ Flexible schema (user metadata, event logs)
✅ Cần horizontal scale (hàng tỷ documents)
✅ Document structure hợp lý (product catalog)
❌ Cần ACID transactions
❌ Complex relationships (dùng SQL)
```

## 7. Code Review Checklist

> **🔍 WHAT:** Code Review là quá trình một developer khác đọc và nhận xét code trước khi merge – kiểm tra correctness, security, performance, readability và consistency với conventions.
>
> **💡 WHY:** Bug đắt nhất là bug lọt ra production. Code review bắt bug sớm (trong development phase), share knowledge trong team, đảm bảo code quality đồng đều, ngăn security vulnerability. Đây là nơi junior học từ senior.
>
> **⚙️ HOW:** Review theo checklist có cấu trúc. Focus vào logic và security, không tranh luận về style (để linter/formatter giải quyết). Nhận xét constructive, giải thích lý do. Approve khi code đạt tiêu chuẩn.
>
> **📍 WHEN/WHERE:** Mọi PR trước khi merge vào develop/main. Bắt buộc ít nhất 1 reviewer approval. Code author không được tự merge PR của mình. Senior review với junior thường xuyên để transfer knowledge.

### ✅ Code Review Checklist tiêu chuẩn

#### Correctness
- [ ] Logic đúng với requirements
- [ ] Edge cases được xử lý (null, empty list, negative)
- [ ] Error handling đầy đủ và có ý nghĩa
- [ ] Transaction boundaries đúng

#### Security
- [ ] Không hardcode credentials/secret
- [ ] Input được validate và sanitize
- [ ] Authorization check đúng (kiểm tra ownership)
- [ ] Không log sensitive data

#### Performance
- [ ] Không có N+1 query
- [ ] Có pagination cho list response
- [ ] Index cho các cột thường query
- [ ] Không load toàn bộ data vào memory

#### Code Quality
- [ ] Tên biến/method rõ ràng, mô tả đúng
- [ ] Function/method nhỏ, đúng 1 trách nhiệm
- [ ] Không có dead code hay TODO cũ
- [ ] Unit test cho business logic

#### Spring Boot Specific
- [ ] Constructor injection (không field injection)
- [ ] @Transactional đặt đúng chỗ (Service, không Controller)
- [ ] Trả DTO, không trả Entity trực tiếp
- [ ] Custom exception với message rõ ràng

## 8. Lộ trình tiếp theo (Senior level)

> **🔍 WHAT:** Sau khi nắm vững roadmap từ 00-15, hướng đi Senior Backend bao gồm: kiến trúc nâng cao, Kubernetes, event-driven architecture, DDD (Domain Driven Design), performance engineering, technical leadership.
>
> **💡 WHY:** Junior biết HOW (cách implement). Senior biết WHY (tại sao chọn giải pháp này), WHEN (khi nào dùng), và WHAT-IF (trade-off). Level up liên tục là yêu cầu trong ngành phần mềm.
>
> **⚙️ HOW:** Học qua: làm project thực tế và xử lý production issues, đọc architecture articles (highscalability.com), contribute open source, mentor junior developers, lead technical discussions.
>
> **📍 WHEN/WHERE:** Sau 2-3 năm kinh nghiệm Java Backend. Đọc case studies của companies (Netflix, Uber, Airbnb) về cách họ scale. System design interviews là benchmark để biết mình ở level nào.
