# 08. Spring Data JPA & Hibernate

> **Mục tiêu:** Thành thạo ORM với JPA/Hibernate, viết query hiệu quả và xử lý mối quan hệ giữa Entity.

---

## 1. JPA & Hibernate là gì?

> **🔍 WHAT:** JPA (Java Persistence API) là đặc tả (specification) chuẩn cho ORM trong Java. Hibernate là implementation phổ biến nhất của JPA. Spring Data JPA là lớp abstraction trên Hibernate, giảm boilerplate code.
>
> **💡 WHY:** Thay vì viết SQL thủ công và mapping kết quả về Java object, JPA/Hibernate tự động hóa điều này – tiết kiệm thời gian, giảm lỗi, code hướng object thay vì hướng bảng.
>
> **⚙️ HOW:** Annotate class Java với `@Entity` để ánh xạ thành bảng DB. Spring Data JPA tự generate SQL từ method name (`findByEmail`), JPQL query (`@Query`), hoặc native SQL. Hibernate quản lý Session/EntityManager bên dưới.
>
> **📍 WHEN/WHERE:** Tầng Repository của mọi dự án Spring Boot có database. Thay thế hoàn toàn JDBC thủ công – chỉ dùng native query khi JPQL không đủ mạnh (complex analytics, stored procedure).

```
Java Application
      ↓
  Spring Data JPA   ← Convenience layer (findByEmail, @Query)
      ↓
  JPA (Spec/API)    ← Standard interface (@Entity, EntityManager)
      ↓
  Hibernate (ORM)    ← Implementation (generates SQL, manages cache)
      ↓
   Database
```

## 2. Entity Mapping

> **🔍 WHAT:** Entity là Java class được annotate `@Entity` để ánh xạ 1-1 với bảng trong database. Mỗi field tương ứng một cột, mỗi instance tương ứng một row.
>
> **💡 WHY:** Thay vì làm việc với ResultSet và String column name (dễ typo, không type-safe), Entity cho phép làm việc với Java object có kiểu dữ liệu rõ ràng, được compiler kiểm tra.
>
> **⚙️ HOW:** Dùng `@Entity`, `@Table`, `@Id`, `@GeneratedValue`, `@Column` để cấu hình ánh xạ. `@CreatedDate`, `@LastModifiedDate` của Spring Data Auditing tự điền timestamp. Kết hợp Lombok để giảm boilerplate.
>
> **📍 WHEN/WHERE:** Mỗi bảng trong DB tương ứng một Entity class trong package `entity/` hoặc `model/`. Entity KHÔNG nên exposed trực tiếp ra REST API – dùng DTO để chuyển đổi.

```java
@Entity
@Table(name = "users", indexes = {
    @Index(name = "idx_user_email", columnList = "email")
})
@Data @Builder @NoArgsConstructor @AllArgsConstructor
@EntityListeners(AuditingEntityListener.class)
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email", nullable = false, unique = true, length = 255)
    private String email;

    @Column(name = "full_name", nullable = false, length = 100)
    private String fullName;

    @Enumerated(EnumType.STRING)  // lưu "USER", "ADMIN" thay vì 0, 1
    @Column(nullable = false)
    private Role role = Role.USER;

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}

// Kích hoạt Auditing
@Configuration
@EnableJpaAuditing
public class JpaConfig {}
```

> **📝 Giải thích chi tiết code Entity:**
> * `@Entity`: Khai báo với JPA rằng class `User` này là một thực thể (Entity) được ánh xạ trực tiếp thành một bảng trong cơ sở dữ liệu. Lớp này bắt buộc phải có một Constructor rỗng (no-argument constructor).
> * `@Table(name = "users", indexes = ...)`:
>   * `name = "users"`: Đặt tên tường minh cho bảng trong database là `users` thay vì sử dụng tên class viết thường mặc định.
>   * `indexes`: Khai báo tạo Index trực tiếp từ cấu trúc code Java Entity. Lệnh này sẽ được Flyway hoặc Hibernate dọn dẹp để tự động tạo index tên `idx_user_email` cho cột `email` trong database.
> * `@EntityListeners(AuditingEntityListener.class)`: Kích hoạt bộ lắng nghe thay đổi thực thể (Auditing Entity Listener) của Spring. Nó tự động theo dõi, thu thập dữ liệu thời gian tạo và chỉnh sửa để gán cho các cột tương ứng.
> * `@Id`: Đánh dấu thuộc tính `id` đóng vai trò là **Khóa chính (Primary Key)** của bảng.
> * `@GeneratedValue(strategy = GenerationType.IDENTITY)`: Chỉ định chiến lược tự động sinh giá trị cho khóa chính. Giá trị `IDENTITY` giao phó toàn quyền cho database tự động sinh ID tự tăng khi chạy (như `AUTO_INCREMENT` trong MySQL, hoặc cột `SERIAL` trong PostgreSQL).
> * `@Column(name = "email", nullable = false...)`: Ánh xạ thuộc tính Java vào cột tương ứng trong bảng:
>   * `name`: Đặt tên cột trong bảng.
>   * `nullable = false`: Ràng buộc cột bắt buộc phải có giá trị (NOT NULL).
>   * `unique = true`: Ràng buộc cột email không được trùng lặp.
> * `@Enumerated(EnumType.STRING)`: Ràng buộc lưu giá trị của kiểu dữ liệu Enum. Mặc định JPA sẽ lưu chỉ mục số của Enum (`0` cho `USER`, `1` cho `ADMIN`). Việc đổi sang `EnumType.STRING` ép hệ thống lưu trực tiếp dạng chuỗi văn bản (`"USER"`, `"ADMIN"`) vào database. Điều này giúp database dễ đọc và tránh bị sai lệch dữ liệu nếu sau này bạn thay đổi thứ tự khai báo enum trong code Java.
> * `@CreatedDate` / `@LastModifiedDate`: Hai annotation siêu tiện lợi. Kết hợp với việc bật `@EnableJpaAuditing` ở file config, Spring Boot sẽ **tự động điền thời gian hiện tại** vào trường `createdAt` khi tạo mới record và tự động cập nhật trường `updatedAt` mỗi khi record được chỉnh sửa mà ta không cần viết code gán thủ công (`user.setCreatedAt(LocalDateTime.now())`).
> * `@Column(updatable = false)`: Ngăn không cho Hibernate sinh ra code cập nhật trường `createdAt` trong câu lệnh SQL `UPDATE`. Đảm bảo thời gian khởi tạo luôn luôn bất biến trong suốt vòng đời của row dữ liệu.

## 3. Entity Relationships

> **🔍 WHAT:** Relationships là cách JPA biểu diễn mối quan hệ giữa các Entity: `@OneToMany` (1 user nhiều orders), `@ManyToOne` (nhiều orders thuộc 1 user), `@ManyToMany`, `@OneToOne`.
>
> **💡 WHY:** Database dùng foreign key để biểu diễn quan hệ. JPA tự động dịch relationship annotations thành JOIN query, cho phép navigate từ object này sang object khác (`order.getUser().getName()`) mà không cần viết JOIN thủ công.
>
> **⚙️ HOW:** Chọn `FetchType.LAZY` (default cho collection, khuyến nghị) hoặc `EAGER` (load ngay khi query cha). `CascadeType.ALL` tự động cascade save/delete sang entity liên quan. `orphanRemoval=true` tự xóa child khi bị remove khỏi collection.
>
> **📍 WHEN/WHERE:** Thiết kế relationship khi tạo Entity. Cẩn thận với EAGER fetch (N+1 problem). Dùng `@JsonIgnore` hoặc DTO để tránh vòng lặp JSON khi serialize bidirectional relationship.

```java
// Order (1) → OrderItems (N)
@Entity
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)  // LAZY – chỉ load khi cần
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();
}

@Entity
public class OrderItem {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    @JsonIgnore  // tránh vòng lặp JSON khi serialize
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
    private BigDecimal unitPrice;
}

// ManyToMany – Student ↔ Course
@Entity
public class Student {
    @ManyToMany
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();
}
```

> **📝 Giải thích chi tiết code Relationships:**
> * `@ManyToOne(fetch = FetchType.LAZY)`: Khai báo mối quan hệ Nhiều - Một (Nhiều Order thuộc về 1 User).
>   * `FetchType.LAZY` (Tải chậm): Đây là **Best Practice bắt buộc**. Khi bạn thực hiện câu query lấy thông tin `Order`, Hibernate chỉ lấy thông tin của bảng `Order` mà **hoàn toàn không truy vấn bảng User**. Chỉ khi nào trong code bạn gọi hàm truy cập sâu: `order.getUser().getName()`, Hibernate mới thực thi thêm 1 câu query phụ để lấy thông tin User lên. Điều này giúp tối ưu hóa bộ nhớ và hiệu suất của hệ thống.
> * `@JoinColumn(name = "user_id")`: Định nghĩa cột khóa ngoại (Foreign Key) thực tế trong bảng `orders` sẽ mang tên là `user_id`.
> * `@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)`: Khai báo mối quan hệ Một - Nhiều (1 Order chứa nhiều OrderItem).
>   * `mappedBy = "order"`: Chỉ định rằng mối quan hệ này là quan hệ hai chiều (bidirectional) và được làm chủ (owned) bởi trường `order` bên phía đối tượng `OrderItem`.
>   * `cascade = CascadeType.ALL`: Bật lan truyền hành vi. Khi ta lưu đối tượng `Order`, toàn bộ danh sách `OrderItem` con bên trong nó sẽ **tự động được lưu theo** vào DB chỉ với 1 lệnh `orderRepository.save(order)`. Tương tự khi xóa `Order`, các item con cũng tự động bị xóa theo.
>   * `orphanRemoval = true`: Cơ chế tự dọn dẹp dữ liệu mồ côi. Nếu bạn xóa một `OrderItem` ra khỏi danh sách `items` của `Order` trong Java (`order.getItems().remove(0)`), Hibernate sẽ tự động sinh câu lệnh SQL `DELETE` để xóa record tương ứng của item đó ra khỏi database.
> * `@JsonIgnore`: Rất quan trọng khi dùng quan hệ 2 chiều. Nó chỉ thị cho thư viện Jackson (thư viện chuyển đổi Object sang JSON mặc định của Spring Boot) bỏ qua không chuyển đổi trường này sang JSON. Nếu không có annotation này, quá trình chuyển đổi JSON sẽ bị rơi vào **vòng lặp vô hạn (Infinite Recursion)** (Order gọi Item, Item gọi ngược lại Order...) làm sập ứng dụng (StackOverflowError).
> * `@JoinTable`: Dùng để cấu hình bảng trung gian `student_courses` cho mối quan hệ Nhiều - Nhiều (`@ManyToMany`). Bảng trung gian này sẽ chứa hai cột khóa ngoại là `student_id` và `course_id`.

## 4. Repository

> **🔍 WHAT:** Repository trong Spring Data JPA là interface kế thừa `JpaRepository<Entity, ID>` – Spring tự động tạo implementation với hàng chục method CRUD sẵn có và cho phép định nghĩa query bằng method name.
>
> **💡 WHY:** Không cần viết SQL cơ bản (findAll, save, deleteById...). Method name như `findByEmailAndActive` tự sinh SQL `WHERE email = ? AND active = ?`. Giảm 90% boilerplate code so với JDBC.
>
> **⚙️ HOW:** Kế thừa `JpaRepository`. Spring Data tự parse method name theo convention để generate query. Dùng `@Query` cho query phức tạp hơn. `@Modifying + @Transactional` cho UPDATE/DELETE query.
>
> **📍 WHEN/WHERE:** Mỗi Entity có 1 Repository interface trong package `repository/`. Service inject Repository để thao tác DB. Không để business logic trong Repository – chỉ data access thuần túy.

```java
@Repository
public interface UserRepository extends JpaRepository<User, Long> {

    // Spring Data tự generate SQL từ method name
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
    List<User> findByActiveTrue();
    List<User> findByFullNameContainingIgnoreCase(String name);
    Page<User> findByRole(Role role, Pageable pageable);
    long countByRole(Role role);

    // @Query với JPQL
    @Query("SELECT u FROM User u WHERE u.createdAt BETWEEN :start AND :end AND u.active = true")
    List<User> findActiveUsersInPeriod(
        @Param("start") LocalDateTime start,
        @Param("end") LocalDateTime end
    );

    // Native SQL
    @Query(value = "SELECT * FROM users WHERE EXTRACT(YEAR FROM created_at) = :year",
           nativeQuery = true)
    List<User> findUsersRegisteredInYear(@Param("year") int year);

    // UPDATE với @Modifying
    @Modifying
    @Transactional
    @Query("UPDATE User u SET u.active = false WHERE u.id = :id")
    int deactivateUser(@Param("id") Long id);
}
```

> **📝 Giải thích chi tiết code Repository:**
> * `JpaRepository<User, Long>`: Khai báo interface kế thừa `JpaRepository` truyền vào kiểu Entity quản lý là `User` và kiểu dữ liệu của khóa chính là `Long`.
> * `findByFullNameContainingIgnoreCase(String name)`: Sức mạnh của **Query Creation** của Spring. Lệnh này sẽ tự động được dịch sang câu SQL tương đương: `SELECT * FROM users WHERE LOWER(full_name) LIKE LOWER(CONCAT('%', ?, '%'))`. Giúp tìm kiếm không phân biệt hoa thường.
> * `@Query("SELECT u FROM User u ...")`: Viết câu lệnh truy vấn bằng ngôn ngữ **JPQL (Java Persistence Query Language)**. Điểm khác biệt lớn của JPQL so với SQL là ta không thao tác trực tiếp trên tên bảng hay tên cột vật lý của database, mà thao tác hoàn toàn trên tên các Class Entity Java (`User` viết hoa chữ U) và các thuộc tính tương ứng của nó (`u.active`). Giúp câu query độc lập hoàn toàn với database vật lý bên dưới (dễ dàng đổi DB từ MySQL sang Oracle mà không cần viết lại query).
> * `nativeQuery = true`: Ép buộc sử dụng câu lệnh **SQL thuần (Native SQL)** của database vật lý. Dùng trường hợp này khi cần sử dụng các tính năng hoặc hàm đặc thù của database đó (như hàm `EXTRACT` trong PostgreSQL) mà JPQL không hỗ trợ.
> * `@Modifying` + `@Transactional`: Cần thiết khi viết custom query cho các tác vụ cập nhật (`UPDATE`) hoặc xóa (`DELETE`) dữ liệu bằng `@Query`.
>   * `@Modifying`: Chỉ thị cho Spring Boot biết câu query này sẽ làm biến đổi trạng thái của database (để Hibernate tự động dọn dẹp các cache thực thể trong Session).
>   * `@Transactional`: Mở transaction cho riêng câu lệnh cập nhật này.

## 5. Transactions

> **🔍 WHAT:** `@Transactional` annotation trong Spring tự động bắt đầu transaction khi vào method và commit khi kết thúc thành công. Nếu có `RuntimeException` thì tự động rollback.
>
> **💡 WHY:** Đảm bảo tính toàn vẹn khi một nghiệp vụ cần nhiều thao tác DB. Không cần viết `BEGIN/COMMIT/ROLLBACK` thủ công. Spring AOP bọc method và quản lý transaction lifecycle.
>
> **⚙️ HOW:** Đặt `@Transactional` ở Service method (không phải Repository hay Controller). `readOnly = true` tối ưu cho read-only operations. Propagation và isolation level có thể tùy chỉnh cho advanced use case.
>
> **📍 WHEN/WHERE:** Mọi Service method tạo/sửa/xóa data cần `@Transactional`. Đặc biệt quan trọng khi một operation cần nhiều thay đổi DB phải thành công đồng thời (đặt hàng = tạo order + giảm stock).

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional  // auto COMMIT/ROLLBACK
    public Order createOrder(CreateOrderRequest request) {
        // Giảm stock – nếu lỗi ở bước này hoặc sau, toàn bộ rollback
        int updated = productRepository.decreaseStock(request.getProductId(), request.getQuantity());
        if (updated == 0) throw new InsufficientStockException("Sản phẩm hết hàng");

        Order order = buildOrder(request);
        return orderRepository.save(order);
        // RuntimeException → ROLLBACK, không RuntimeException → COMMIT
    }

    @Transactional(readOnly = true)  // tối ưu: không tạo write lock
    public Page<OrderResponse> getUserOrders(Long userId, Pageable pageable) {
        return orderRepository.findByUserId(userId, pageable).map(this::toResponse);
    }

    // Propagation.REQUIRES_NEW – transaction riêng, commit độc lập
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAudit(String action) {
        auditRepository.save(new AuditLog(action)); // commit dù outer transaction fail
    }
}
```

> **📝 Giải thích chi tiết code Transactions:**
> * `@Transactional`: Spring Boot sử dụng cơ chế Dynamic Proxy để bọc ngoài phương thức. Nó tự động mở một transaction khi bắt đầu gọi hàm `createOrder`. Nếu quá trình chạy hàm xảy ra lỗi và ném ra một ngoại lệ unchecked (`RuntimeException` hoặc lớp con của nó), Spring sẽ tự động kích hoạt `ROLLBACK` toàn bộ dữ liệu. Nếu hàm hoàn thành bình thường, hệ thống tự động gọi `COMMIT` lên DB.
> * `readOnly = true`: Đánh dấu giao dịch chỉ đọc. Cấu hình này giúp tối ưu hóa hiệu suất cực lớn: Hibernate sẽ tự động tắt tính năng **Dirty Checking** (kiểm tra sự thay đổi trạng thái của đối tượng để tự động sinh câu UPDATE), đồng thời một số database (như PostgreSQL) sẽ tối ưu hóa việc phân phối query tới các node DB Slave chuyên đọc.
> * `propagation = Propagation.REQUIRES_NEW`: Cấu hình chiến lược truyền dẫn Transaction (Transaction Propagation). Giá trị `REQUIRES_NEW` chỉ định Spring sẽ **tạm dừng giao dịch hiện tại** của luồng code và mở một giao dịch mới độc lập hoàn toàn cho hàm `logAudit`. Nhờ đó, hành động ghi nhật ký hệ thống (Audit Log) vẫn sẽ được lưu trữ vĩnh viễn (COMMIT) thành công vào database ngay cả khi toàn bộ quá trình đặt hàng bên ngoài bị lỗi và phải ROLLBACK dữ liệu.

## 6. N+1 Problem & Solutions

> **🔍 WHAT:** N+1 Problem là antipattern xảy ra khi query 1 list entity (1 query) rồi access lazy-loaded relationship của từng entity trong vòng lặp (N query thêm) – tổng N+1 queries thay vì 1.
>
> **💡 WHY:** Gây performance catastrophe – load 100 orders + 100 query load user của từng order = 101 queries. Với 1000 orders là 1001 queries. Phải phát hiện và fix trước khi ra production.
>
> **⚙️ HOW:** Giải pháp: **JOIN FETCH** trong JPQL (1 query với JOIN), `@EntityGraph` (tương tự nhưng khai báo declarative), `@BatchSize` (N batch queries thay vì N single queries), hoặc DTO projection (chỉ select field cần).
>
> **📍 WHEN/WHERE:** Kiểm tra N+1 bằng cách enable `spring.jpa.show-sql=true` và đếm số query. Xảy ra khi access navigation property (`order.getUser()`) trong vòng lặp sau khi fetch list. Dùng Hibernate Statistics hoặc Datasource Proxy để detect.

```java
// ❌ N+1 Problem
List<Order> orders = orderRepository.findAll();
for (Order order : orders) {
    System.out.println(order.getUser().getName()); // Mỗi lần = 1 query!
}
// → 1 + N queries (1 SELECT orders + N SELECT users)

// ✅ Solution 1: JOIN FETCH trong JPQL
@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE o.status = :status")
List<Order> findByStatusWithUser(@Param("status") OrderStatus status);

// ✅ Solution 2: @EntityGraph (declarative)
@EntityGraph(attributePaths = {"user", "items", "items.product"})
List<Order> findAll();

// ✅ Solution 3: @BatchSize (cho collection)
@OneToMany(mappedBy = "order")
@BatchSize(size = 30)  // load 30 collections cùng lúc thay vì 1 từng cái
private List<OrderItem> items;

// ✅ Solution 4: DTO Projection – chỉ select field cần
@Query("""
    SELECT new com.example.dto.OrderSummaryDTO(o.id, u.fullName, o.total)
    FROM Order o JOIN o.user u
    WHERE o.status = :status
    """)
List<OrderSummaryDTO> findOrderSummaries(@Param("status") OrderStatus status);
```

> **📝 Giải thích chi tiết các giải pháp sửa lỗi N+1:**
> * **Tại sao xảy ra N+1?** Ở đoạn code lỗi, dòng `orderRepository.findAll()` sinh ra **1 câu query** lấy danh sách N hóa đơn. Tuy nhiên, vì `user` là LAZY fetch nên nó chỉ mang giá trị Proxy (rỗng). Khi chạy vòng lặp và gọi `order.getUser().getName()`, Hibernate bắt buộc phải gửi thêm **N câu query** nữa để lấy thông tin của từng User tương ứng.
> * **Giải pháp 1 (`JOIN FETCH`)**: Sử dụng từ khóa `JOIN FETCH` trong JPQL. Hibernate sẽ tự động dịch sang câu lệnh SQL chứa mệnh đề kết hợp `INNER JOIN` hoặc `LEFT JOIN` để nạp (load) toàn bộ thông tin User lên ngay trong **1 câu query duy nhất**.
> * **Giải pháp 2 (`@EntityGraph`)**: Một giải pháp tinh tế không cần viết tay JPQL. Annotation chỉ thị cho Spring Data JPA nạp trước (Eager load) các thuộc tính liên kết được chỉ định trong danh sách (`user`, `items`...) bằng cách tự động sinh câu query JOIN.
> * **Giải pháp 3 (`@BatchSize(size = 30)`)**: Giảm số lượng truy vấn bằng cách gom nhóm (batching). Khi bạn truy cập item đầu tiên, Hibernate sẽ tự động nạp trước items của 30 hóa đơn kế tiếp chỉ bằng **1 câu query sử dụng toán tử IN** (`WHERE order_id IN (1, 2, ... 30)`) thay vì gửi 30 câu truy vấn đơn lẻ.
> * **Giải pháp 4 (`DTO Projection`)**: Phương pháp tối ưu hiệu suất triệt để nhất. Ta sử dụng cú pháp JPQL `new com.example.dto.OrderSummaryDTO(...)` để ép buộc Hibernate chỉ sinh câu query SELECT đúng 3 trường dữ liệu cần thiết thay vì SELECT toàn bộ các cột của bảng, giúp tiết kiệm băng thông mạng và RAM cực lớn.

## 7. Database Migration với Flyway

> **🔍 WHAT:** Flyway là công cụ quản lý database migration – theo dõi lịch sử thay đổi schema DB qua các file SQL có version, đảm bảo DB của mọi environment (dev/staging/prod) đồng bộ.
>
> **💡 WHY:** Không có migration tool, mỗi developer và server có thể có schema DB khác nhau – dẫn đến lỗi khó debug. `ddl-auto=update` của Hibernate không phù hợp production vì không rollback được và không log thay đổi.
>
> **⚙️ HOW:** Tạo file SQL theo format `V{version}__{description}.sql` trong `db/migration/`. Flyway đọc và chạy các file này theo thứ tự version khi app khởi động. Mỗi migration chỉ chạy 1 lần (tracked trong `flyway_schema_history` table).
>
> **📍 WHEN/WHERE:** Bắt buộc trong production environment. Thay thế `ddl-auto=update/create` bằng `ddl-auto=validate` + Flyway. Mỗi thay đổi schema (thêm cột, tạo index, thêm bảng) → tạo migration file mới.

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: validate  # validate schema thay vì auto-create
```

```sql
-- src/main/resources/db/migration/V1__create_users_table.sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    full_name VARCHAR(100) NOT NULL,
    password VARCHAR(255) NOT NULL,
    role VARCHAR(20) DEFAULT 'USER' NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- V2__add_index_to_users.sql (migration kế tiếp)
CREATE INDEX idx_user_role ON users(role);
ALTER TABLE users ADD COLUMN phone VARCHAR(20);
```

> **📝 Giải thích chi tiết cấu hình Flyway:**
> * `V{version}__{description}.sql`: Định dạng quy ước đặt tên file của Flyway. Lưu ý phần phân tách giữa version và mô tả là **2 dấu gạch dưới liên tiếp (`__`)**. Flyway sẽ quét thư mục này và sắp xếp chạy các file theo thứ tự phiên bản tăng dần.
> * `flyway_schema_history`: Khi ứng dụng chạy lần đầu, Flyway tự tạo một bảng đặc biệt tên là `flyway_schema_history` để ghi nhận nhật ký các file migration nào đã chạy thành công (bao gồm mã hash của file). Lần khởi động tiếp theo, Flyway so sánh các file trong code với bảng lịch sử này để chỉ chạy các file mới bổ sung, ngăn chặn việc chạy lại các file cũ.
> * **Quy tắc vàng của Flyway**: Tuyệt đối **không bao giờ được phép chỉnh sửa nội dung của một file migration đã được chạy thành công** trước đó. Nếu bạn muốn thêm cột hay thay đổi kiểu dữ liệu, bạn bắt buộc phải tạo một file phiên bản mới tiếp theo (ví dụ: `V3__...`) để thực hiện sửa đổi.
