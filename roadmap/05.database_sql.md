# 05. Cơ sở dữ liệu & SQL

> **Mục tiêu:** Nắm vững SQL cơ bản đến nâng cao, thiết kế CSDL chuẩn hóa và kết nối Java với database.

---

## 1. Thiết kế cơ sở dữ liệu

> **🔍 WHAT:** Thiết kế CSDL là quá trình xác định cấu trúc bảng, cột, kiểu dữ liệu, khóa chính/ngoại và mối quan hệ giữa các thực thể để lưu trữ dữ liệu hiệu quả.
>
> **💡 WHY:** Schema được thiết kế tốt giúp truy vấn nhanh, dữ liệu nhất quán, dễ mở rộng. Schema xấu dẫn đến dữ liệu trùng lặp, khó query, hiệu suất kém và tốn kém khi refactor.
>
> **⚙️ HOW:** Bắt đầu từ entity-relationship diagram (ERD), áp dụng chuẩn hóa (1NF→3NF) để loại bỏ trùng lặp, xác định PK/FK, sau đó viết DDL SQL để tạo bảng.
>
> **📍 WHEN/WHERE:** Bước đầu tiên khi thiết kế hệ thống – xác định schema trước khi viết Entity class trong Spring Boot. Schema quyết định structure của toàn bộ ứng dụng.

### Các khái niệm cơ bản

| Khái niệm | Giải thích |
|-----------|-----------|
| **Table** | Tập hợp dữ liệu có cấu trúc giống nhau |
| **Primary Key** | Định danh duy nhất cho mỗi row |
| **Foreign Key** | Liên kết giữa các bảng |
| **Index** | Tăng tốc tìm kiếm |

### Ví dụ schema E-commerce

```sql
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    email       VARCHAR(255) UNIQUE NOT NULL,
    password    VARCHAR(255) NOT NULL,
    full_name   VARCHAR(100) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_active   BOOLEAN DEFAULT TRUE
);

CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    price       DECIMAL(10, 2) NOT NULL CHECK (price >= 0),
    stock       INT NOT NULL DEFAULT 0,
    category_id INT REFERENCES categories(id),
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    status      VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    total       DECIMAL(10, 2) NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_items (
    id          BIGSERIAL PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id  BIGINT NOT NULL REFERENCES products(id),
    quantity    INT NOT NULL CHECK (quantity > 0),
    unit_price  DECIMAL(10, 2) NOT NULL
);
```

> **📝 Giải thích chi tiết mã SQL DDL:**
> * `BIGSERIAL PRIMARY KEY`: Kiểu dữ liệu số nguyên tự tăng 8-byte (trong PostgreSQL), tương đương với `BIGINT` tự tăng. Nó được chọn làm **Khóa chính (Primary Key)** để đảm bảo mỗi row dữ liệu luôn có định danh duy nhất không trùng lặp và đạt hiệu suất cao khi đánh index.
> * `VARCHAR(255) UNIQUE NOT NULL`: Định nghĩa cột email chứa chuỗi văn bản dài tối đa 255 ký tự. Ràng buộc `UNIQUE` đảm bảo không có 2 tài khoản trùng email; `NOT NULL` cấm lưu dữ liệu trống (rỗng).
> * `DECIMAL(10, 2)`: Kiểu số thập phân có độ chính xác cố định (tối đa 10 chữ số, trong đó có 2 chữ số sau dấu phẩy). Dùng kiểu này để lưu số tiền thay vì `FLOAT` hoặc `DOUBLE` để tránh các sai số làm tròn số học nhị phân nguy hiểm.
> * `CHECK (price >= 0)`: **Ràng buộc kiểm tra (Check Constraint)** ở mức database. Nó chặn đứng bất kỳ câu lệnh nào cố tình thêm sản phẩm có mức giá âm.
> * `REFERENCES users(id)`: Khai báo **Khóa ngoại (Foreign Key)**. Cột `user_id` của bảng `orders` sẽ liên kết và phụ thuộc trực tiếp vào cột `id` của bảng `users`. Điều này ngăn việc tạo đơn hàng cho một user không tồn tại (Đảm bảo tính toàn vẹn tham chiếu - Referential Integrity).
> * `ON DELETE CASCADE`: Khi một bản ghi của bảng cha `orders` bị xóa, toàn bộ các bản ghi con liên quan trong `order_items` sẽ **tự động bị xóa sạch** theo. Nó giúp tránh việc tồn tại dữ liệu mồ côi (orphan data) trong database.

## 2. SQL Cơ bản (CRUD)

> **🔍 WHAT:** CRUD là 4 thao tác cơ bản với database: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE) – tương ứng với HTTP POST, GET, PUT/PATCH, DELETE trong REST API.
>
> **💡 WHY:** Đây là nền tảng của mọi thao tác database. Dù dùng ORM như Hibernate, bên dưới vẫn là các câu SQL này – hiểu SQL giúp debug query, tối ưu hiệu suất và giải quyết các vấn đề mà ORM không xử lý được.
>
> **⚙️ HOW:** `SELECT` để truy vấn với `WHERE`, `ORDER BY`, `LIMIT`. `INSERT INTO...VALUES` để thêm dữ liệu. `UPDATE...SET...WHERE` để sửa. `DELETE FROM...WHERE` để xóa – luôn có `WHERE` tránh xóa/sửa hết bảng.
>
> **📍 WHEN/WHERE:** Dùng trực tiếp trong JDBC hoặc native query của Spring Data JPA. Trong phát triển hàng ngày, hiểu SQL để đọc được Hibernate-generated queries trong log và tối ưu chúng.

```sql
-- SELECT với các điều kiện
SELECT * FROM users WHERE is_active = TRUE;
SELECT * FROM products WHERE price BETWEEN 100000 AND 500000;
SELECT * FROM users WHERE email LIKE '%@gmail.com';
SELECT * FROM products WHERE category_id IN (1, 2, 3);
SELECT * FROM users WHERE phone IS NOT NULL;

-- ORDER BY và LIMIT (phân trang)
SELECT * FROM products ORDER BY price DESC LIMIT 10 OFFSET 20;

-- INSERT
INSERT INTO users (email, password, full_name)
VALUES ('alice@example.com', 'hashed_password', 'Alice Nguyen');

-- UPDATE
UPDATE products SET price = price * 0.9 WHERE category_id = 1;

-- DELETE (cẩn thận – luôn dùng WHERE!)
DELETE FROM users WHERE is_active = FALSE AND created_at < '2023-01-01';
```

> **📝 Giải thích chi tiết mã SQL:**
> * `WHERE price BETWEEN 100000 AND 500000`: Lọc các sản phẩm có khoảng giá trị từ 100,000 đến 500,000 (bao gồm cả hai cận).
> * `email LIKE '%@gmail.com'`: Tìm kiếm chuỗi sử dụng ký tự đại diện `%` (đại diện cho bất kỳ chuỗi ký tự nào). Lệnh này lọc ra tất cả user sử dụng Gmail.
> * `category_id IN (1, 2, 3)`: Lọc sản phẩm thuộc một trong ba danh mục có ID tương ứng, ngắn gọn hơn việc viết `category_id = 1 OR category_id = 2 OR category_id = 3`.
> * `ORDER BY price DESC LIMIT 10 OFFSET 20`:
>   * `ORDER BY price DESC`: Sắp xếp sản phẩm theo giá giảm dần (`DESC` - Descending).
>   * `LIMIT 10`: Lấy đúng 10 bản ghi đầu tiên trong danh sách đã sắp xếp.
>   * `OFFSET 20`: Bỏ qua 20 bản ghi đầu tiên. Đây là mô-típ phân trang (Pagination) chuẩn trong SQL (lấy trang số 3, mỗi trang có 10 phần tử).
> * `UPDATE ... SET price = price * 0.9 WHERE ...`: Giảm giá 10% cho toàn bộ sản phẩm thuộc danh mục có ID = 1. Cực kỳ quan trọng: Nếu không viết mệnh đề `WHERE`, toàn bộ sản phẩm trong database sẽ bị giảm giá!

## 3. SQL Nâng cao

> **🔍 WHAT:** SQL nâng cao gồm JOIN (kết hợp dữ liệu nhiều bảng), GROUP BY (tổng hợp), Window Functions (tính toán trong partitions), CTE (Common Table Expression – query tạm thời có tên).
>
> **💡 WHY:** Ứng dụng thực tế cần báo cáo, phân tích, tổng hợp dữ liệu từ nhiều bảng. Không có JOIN thì phải load dữ liệu về Java rồi xử lý – rất chậm. SQL nâng cao giúp xử lý phức tạp ngay ở tầng DB, nhanh hơn nhiều.
>
> **⚙️ HOW:** `INNER JOIN` lấy dữ liệu tồn tại ở cả 2 bảng; `LEFT JOIN` lấy tất cả từ bảng trái kể cả không khớp bảng phải. `GROUP BY` + aggregate functions (`COUNT`, `SUM`, `AVG`). `HAVING` để filter sau GROUP BY.
>
> **📍 WHEN/WHERE:** Dashboard/báo cáo cần tổng hợp; query thống kê (doanh thu theo tháng, top sản phẩm); Native queries trong Spring Data JPA khi JPQL không đủ mạnh.

```sql
-- INNER JOIN
SELECT o.id, u.email, o.total, o.status
FROM orders o
INNER JOIN users u ON o.user_id = u.id;

-- LEFT JOIN – đếm orders của mỗi user kể cả user chưa có order
SELECT u.email, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.email;

-- GROUP BY + HAVING
SELECT user_id, SUM(total) AS total_spent
FROM orders WHERE status = 'DELIVERED'
GROUP BY user_id
HAVING SUM(total) > 5000000
ORDER BY total_spent DESC;

-- CTE – query có tên, dễ đọc hơn subquery
WITH monthly_revenue AS (
    SELECT DATE_TRUNC('month', created_at) AS month, SUM(total) AS revenue
    FROM orders WHERE status = 'DELIVERED'
    GROUP BY DATE_TRUNC('month', created_at)
)
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS growth
FROM monthly_revenue;

-- Window Function
SELECT name, price, category_id,
       ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC) AS rank_in_cat
FROM products;
```

> **📝 Giải thích chi tiết mã SQL nâng cao:**
> * `INNER JOIN users u ON o.user_id = u.id`: Kết hợp bảng `orders` (viết tắt là `o`) với `users` (viết tắt là `u`) thông qua khóa ngoại. `INNER JOIN` chỉ trả về các dòng dữ liệu mà điều kiện liên kết `ON` khớp ở cả 2 bảng (nghĩa là bỏ qua các đơn hàng không rõ user, hoặc user chưa có đơn hàng nào).
> * `LEFT JOIN ... GROUP BY`:
>   * `LEFT JOIN`: Lấy toàn bộ bản ghi của bảng bên trái (`users`), ngay cả khi không tìm thấy bản ghi liên kết khớp bên bảng bên phải (`orders`). Nếu user chưa có order nào, trường `o.id` sẽ mang giá trị `NULL`.
>   * `COUNT(o.id)`: Đếm số lượng đơn hàng. Lợi thế của việc đếm theo cột `o.id` thay vì đếm sao (`COUNT(*)`) là SQL sẽ bỏ qua các dòng mang giá trị `NULL`, giúp những user chưa mua hàng hiển thị đúng kết quả đếm bằng `0`.
> * `HAVING SUM(total) > 5000000`:
>   * `WHERE status = 'DELIVERED'`: Lọc dữ liệu thô trước khi tiến hành gom nhóm.
>   * `HAVING`: Mệnh đề lọc dữ liệu **sau khi đã gom nhóm bằng GROUP BY**. Ở đây lọc ra các nhóm khách hàng có tổng chi tiêu thực tế lớn hơn 5 triệu. Ta không thể dùng `WHERE SUM(total)` vì `WHERE` không chạy được trên các hàm tổng hợp (Aggregate functions).
> * `WITH monthly_revenue AS (...)`: Sử dụng **CTE (Common Table Expression)**. Định nghĩa một bảng tạm thời tên là `monthly_revenue` giúp chia nhỏ câu query phức tạp cho dễ đọc và tái sử dụng, thay vì viết các subquery lồng nhau cồng kềnh.
>   * `DATE_TRUNC('month', created_at)`: Hàm trong PostgreSQL giúp cắt ngắn mốc thời gian về ngày đầu tiên của tháng đó (ví dụ: `2026-05-25 18:00` -> `2026-05-01 00:00`), dùng để gom nhóm doanh thu theo từng tháng.
>   * `LAG(revenue) OVER (ORDER BY month)`: **Window Function**. Hàm `LAG()` giúp truy xuất và lấy giá trị doanh thu (`revenue`) của dòng dữ liệu ngay phía trước nó (tương đương doanh thu tháng trước) để tính toán chênh lệch tăng trưởng doanh thu (`growth`).
> * `ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC)`: Window Function xếp thứ hạng sản phẩm. `PARTITION BY category_id` giúp chia dữ liệu thành từng nhóm (phân khu) danh mục riêng biệt, sau đó `ROW_NUMBER()` sẽ đánh số thứ tự từ 1 cho sản phẩm có giá từ cao nhất đến thấp nhất (`ORDER BY price DESC`) trong nội bộ phân khu đó.

## 4. Index

> **🔍 WHAT:** Index là cấu trúc dữ liệu phụ (thường là B-tree) được database duy trì song song với bảng để tăng tốc độ tìm kiếm theo cột được index.
>
> **💡 WHY:** Không có index, mỗi truy vấn phải quét toàn bộ bảng (full table scan) – với bảng triệu record sẽ rất chậm. Index đúng chỗ có thể giảm thời gian query từ vài giây xuống milliseconds.
>
> **⚙️ HOW:** Tạo index với `CREATE INDEX`. Dùng `EXPLAIN ANALYZE` để xem query plan và kiểm tra index có được dùng không. Index tốt cho cột: thường dùng trong WHERE, JOIN, ORDER BY; cardinality cao (nhiều giá trị khác nhau).
>
> **📍 WHEN/WHERE:** Index cho foreign key (JPA tự làm), unique key (email, phone), cột thường dùng trong WHERE. Trong Spring Boot, khai báo index trong `@Table(indexes = {...})` của Entity.

```sql
-- Tạo index đơn
CREATE INDEX idx_products_category ON products (category_id);
CREATE INDEX idx_users_email ON users (email);

-- Index kết hợp (dùng cho query filter nhiều cột)
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Unique index
CREATE UNIQUE INDEX idx_users_email_unique ON users (email);

-- Xem query plan (PostgreSQL)
EXPLAIN ANALYZE SELECT * FROM products WHERE category_id = 1;
```

> **📝 Giải thích chi tiết mã SQL:**
> * `CREATE INDEX idx_products_category ON ...`: Tạo cấu trúc cây nhị phân B-Tree phụ trên cột `category_id`. Khi thực hiện tìm kiếm sản phẩm theo danh mục, DB không cần quét toàn bộ bảng từ trên xuống mà tìm trực tiếp trên cây Index với độ phức tạp $O(\log N)$, tăng tốc độ tìm kiếm cực nhanh.
> * `idx_orders_user_status ON orders (user_id, status)`: **Composite Index (Index kết hợp)** trên nhiều cột. Thứ tự cột khai báo rất quan trọng. Index này sẽ hỗ trợ tối ưu cho các query lọc theo `user_id` hoặc lọc đồng thời cả `user_id AND status`. Nhưng nó sẽ **không hỗ trợ** tối ưu cho các query chỉ lọc độc lập theo cột `status`.
> * `EXPLAIN ANALYZE`: Lệnh cực kỳ mạnh mẽ để tối ưu hóa SQL. Thay vì chỉ chạy query, DB sẽ phân tích toàn bộ con đường thực thi câu lệnh (Query Execution Plan), đo lường thời gian thực tế của từng bước và cho bạn biết hệ thống đang dùng thuật toán quét bảng vật lý (Seq Scan - Quét toàn bộ) hay quét thông qua Index (Index Scan) để ta tìm hướng tối ưu index thích hợp.

## 5. Transaction

> **🔍 WHAT:** Transaction là một đơn vị công việc bao gồm nhiều thao tác database được thực hiện như một khối nguyên tử – hoặc tất cả thành công (COMMIT) hoặc tất cả hoàn tác (ROLLBACK).
>
> **💡 WHY:** Đảm bảo tính nhất quán dữ liệu. Ví dụ: chuyển tiền cần cả "trừ A" và "cộng B" thành công – nếu giữa chừng lỗi mà không rollback, tiền sẽ biến mất. Đây là nền tảng của ACID.
>
> **⚙️ HOW:** `BEGIN` bắt đầu transaction, `COMMIT` lưu thay đổi, `ROLLBACK` hoàn tác. Trong Spring Boot, `@Transactional` annotation tự quản lý begin/commit/rollback – exception RuntimeException tự động rollback.
>
> **📍 WHEN/WHERE:** Bất kỳ thao tác nào liên quan đến nhiều bảng cần đồng bộ: đặt hàng (tạo order + giảm stock), chuyển tiền, đăng ký (tạo user + profile). Dùng `@Transactional` ở Service method trong Spring Boot.

```sql
-- Transaction thủ công (JDBC/SQL thuần)
BEGIN;

UPDATE products SET stock = stock - 1 WHERE id = 10 AND stock > 0;
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (100, 10, 1, 299000);
UPDATE orders SET total = total + 299000 WHERE id = 100;

COMMIT;
-- Nếu có lỗi:
ROLLBACK;
```

```java
// Spring Boot – @Transactional tự quản lý
@Service
public class OrderService {
    @Transactional  // auto COMMIT khi thành công, ROLLBACK khi RuntimeException
    public Order createOrder(CreateOrderRequest request) {
        int updated = productRepository.decreaseStock(request.getProductId(), 1);
        if (updated == 0) throw new InsufficientStockException("Hết hàng");
        return orderRepository.save(buildOrder(request));
    }
}
```

> **📝 Giải thích chi tiết code:**
> * `BEGIN;` / `COMMIT;` / `ROLLBACK;`:
>   * `BEGIN`: Khai báo bắt đầu một Transaction. Mọi câu lệnh cập nhật phía sau sẽ tạm thời chỉ ghi nhận ở môi trường cô lập, chưa thay đổi thật sự vào ổ đĩa cứng của hệ thống.
>   * `COMMIT`: Thực thi lưu vĩnh viễn toàn bộ các thay đổi của Transaction đó vào đĩa cứng. Lúc này người dùng khác mới bắt đầu thấy dữ liệu mới.
>   * `ROLLBACK`: Hoàn tác (undo) toàn bộ mọi thay đổi đã làm kể từ lệnh `BEGIN` nếu có bất kỳ dòng lệnh nào trong khối bị lỗi. Database trở về trạng thái y nguyên như lúc chưa chạy Transaction.
> * `@Transactional`: Annotation cực mạnh của Spring Boot để quản lý Transaction khai báo (Declarative Transaction Management). Spring sử dụng cơ chế AOP (Aspect-Oriented Programming) để tự động chèn code mở transaction (`BEGIN`) trước khi vào hàm, tự động gọi `COMMIT` khi hàm thực thi trơn tru kết thúc, và tự động gọi `ROLLBACK` nếu có bất kỳ ngoại lệ Runtime (kế thừa `RuntimeException`) nào bị ném ra trong quá trình chạy hàm.

## 6. Kết nối Java với Database (JDBC)

> **🔍 WHAT:** JDBC (Java Database Connectivity) là API chuẩn của Java để kết nối và thực thi SQL với database – tầng thấp nhất trong Java DB stack.
>
> **💡 WHY:** Hiểu JDBC giúp hiểu bản chất hoạt động của các ORM (Hibernate, JOOQ). Cần JDBC trực tiếp khi cần kiểm soát chi tiết query, bulk operation, hoặc database không được ORM hỗ trợ.
>
> **⚙️ HOW:** `DriverManager.getConnection()` tạo connection; `PreparedStatement` để thực thi parameterized query (tránh SQL injection); `ResultSet` để đọc kết quả. **Luôn** đóng Connection/Statement/ResultSet trong `finally` hoặc `try-with-resources`.
>
> **📍 WHEN/WHERE:** Trong Spring Boot hầu như không dùng JDBC thẳng (dùng JPA/JDBC Template). Nhưng cần hiểu khi debug connection pool, viết native query, hoặc làm việc với legacy code.

```java
// Kết nối và query với JDBC
String url = "jdbc:postgresql://localhost:5432/mydb";

try (Connection conn = DriverManager.getConnection(url, "user", "pass")) {
    // PreparedStatement – tránh SQL Injection
    String sql = "SELECT * FROM products WHERE category_id = ? AND price < ?";
    try (PreparedStatement stmt = conn.prepareStatement(sql)) {
        stmt.setInt(1, 1);
        stmt.setDouble(2, 500000);

        try (ResultSet rs = stmt.executeQuery()) {
            while (rs.next()) {
                System.out.println(rs.getLong("id") + " - " + rs.getString("name"));
            }
        }
    }
} catch (SQLException e) {
    e.printStackTrace();
}
```

> **📝 Giải thích chi tiết code:**
> * `try (Connection conn = ...)`: Sử dụng cơ chế **try-with-resources** để tự động đóng các tài nguyên kết nối đắt đỏ (`Connection`, `PreparedStatement`, `ResultSet`) theo đúng thứ tự ngược lại sau khi dùng xong, tránh triệt để việc rò rỉ kết nối (Connection Leak) làm sập hệ thống database.
> * `PreparedStatement`: Lớp thực thi câu lệnh SQL được biên dịch trước (pre-compiled). Ta không ghép chuỗi String trực tiếp (như `WHERE price < " + input`) mà sử dụng ký tự giữ chỗ `?` và gán giá trị qua `stmt.setInt()`, `stmt.setDouble()`. Cơ chế này chặn hoàn toàn lỗ hổng bảo mật **SQL Injection** nguy hiểm bằng cách ép kiểu và thoát các ký tự đặc biệt của input trước khi gửi tới DB.
> * `ResultSet`: Đối tượng chứa bảng kết quả trả về từ câu query. Hàm `rs.next()` dùng để di chuyển con trỏ dòng (cursor) qua từng hàng dữ liệu từ trên xuống dưới, và `rs.getString("name")` giúp lấy giá trị tại cột `name` của hàng hiện tại.

## 7. Connection Pool (HikariCP)

> **🔍 WHAT:** Connection Pool là tập hợp các database connection được tái sử dụng thay vì tạo mới mỗi lần request – HikariCP là implementation nhanh nhất và được Spring Boot dùng mặc định.
>
> **💡 WHY:** Tạo DB connection tốn nhiều thời gian (~50-100ms). Nếu mỗi request tạo connection mới, server 1000 req/s sẽ tạo 1000 connections/s – quá tải DB. Pool giữ sẵn N connections và tái sử dụng.
>
> **⚙️ HOW:** Spring Boot tự cấu hình HikariCP khi thêm datasource dependency. Điều chỉnh pool size qua `spring.datasource.hikari.*` properties. `maximum-pool-size` nên = (CPU cores * 2) + số disk spindles.
>
> **📍 WHEN/WHERE:** Cấu hình trong `application.yml` cho mọi môi trường. Trong production, tuning pool size dựa vào load testing. Monitoring pool metrics qua Actuator và Prometheus.

```yaml
# application.yml – Spring Boot tự cấu hình HikariCP
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/mydb
    username: myuser
    password: mypassword
    hikari:
      maximum-pool-size: 10      # tối đa 10 connections trong pool
      minimum-idle: 2            # tối thiểu duy trì 2 idle connections
      connection-timeout: 30000  # 30s timeout tối đa khi đợi kết nối rảnh
      idle-timeout: 600000       # tự đóng connection idle sau 10 phút
      max-lifetime: 1800000      # đóng và tạo mới connection sau 30 phút để tránh bị lỗi connection "treo" (stale connection)
```

> **📝 Giải thích chi tiết thuộc tính cấu hình:**
> * `maximum-pool-size: 10`: Giới hạn tối đa số lượng connection đồng thời được kết nối tới database. Nếu cả 10 connection đều đang bận xử lý request, request thứ 11 sẽ phải xếp hàng chờ trong khoảng thời gian quy định tại `connection-timeout`. Việc giới hạn này giúp database tránh khỏi việc quá tải tài nguyên (RAM/CPU) khi hệ thống bị quá tải request đột biến.
> * `minimum-idle: 2`: Số lượng connection luôn luôn được giữ ở trạng thái chờ (rảnh rỗi) sẵn sàng phục vụ ngay lập tức.
> * `connection-timeout: 30000`: Nếu một request đợi rảnh kết nối từ pool quá 30 giây (30,000 ms) mà không lấy được, hệ thống tự động ném ra lỗi Timeout Exception để tránh việc người dùng phải chờ tải trang vô hạn.
