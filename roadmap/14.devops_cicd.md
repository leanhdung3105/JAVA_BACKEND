# 14. DevOps & CI/CD

> **Mục tiêu:** Tự động hóa quy trình build, test, deploy và monitoring ứng dụng.

---

## 1. Git Workflow

> **🔍 WHAT:** Git Workflow là quy ước về cách team sử dụng Git branches và merge strategy. Gitflow (feature/develop/main) và GitHub Flow (feature/main) là 2 mô hình phổ biến nhất.
>
> **💡 WHY:** Không có workflow thống nhất, team sẽ conflict code, khó biết version nào trên production, khó rollback. Workflow chuẩn giúp parallel development, code review bắt buộc và deploy có kiểm soát.
>
> **⚙️ HOW:** GitHub Flow: tạo `feature/tên-tính-năng` từ `main`, code và push, mở Pull Request, review và merge vào main. Mỗi merge vào main trigger CI/CD deploy lên production. Conventional Commits chuẩn hóa message.
>
> **📍 WHEN/WHERE:** Áp dụng ngay từ ngày đầu dự án. Code review qua PR là cơ hội share knowledge và bắt bug. Branch protection rule trên GitHub ngăn push thẳng vào main.

```bash
# GitHub Flow
git checkout -b feature/user-authentication
# code, commit...
git add -A
git commit -m "feat(auth): implement JWT login endpoint"
git push origin feature/user-authentication
# Tạo Pull Request trên GitHub → Review → Merge

# Conventional Commits format: type(scope): description
# type: feat | fix | docs | style | refactor | test | chore
git commit -m "feat(user): add user registration with email verification"
git commit -m "fix(auth): handle expired JWT token correctly"
git commit -m "refactor(order): extract order calculation to service"
git commit -m "test(product): add unit tests for ProductService"
git commit -m "docs: update API documentation for auth endpoints"
```

> **📝 Giải thích chi tiết các lệnh Git và chuẩn Commits:**
> * `git checkout -b`: Tạo mới một nhánh (branch) tên là `feature/user-authentication` từ nhánh hiện tại và tự động chuyển sang làm việc trên nhánh đó. Giúp bảo vệ mã nguồn nhánh `main` luôn ổn định.
> * `git add -A`: Gom toàn bộ các tệp tin được chỉnh sửa, tạo mới và xóa bỏ vào vùng đệm Staging Area để chuẩn bị cho việc tạo commit.
> * **Conventional Commits**: Quy ước quốc tế để chuẩn hóa cách viết thông điệp commit. Nó bao gồm tiền tố:
>   * `feat`: Thêm tính năng mới (Feature).
>   * `fix`: Sửa lỗi (Bug Fix).
>   * `refactor`: Tối ưu cấu trúc code mà không làm thay đổi tính năng bên ngoài.
>   * `test`: Viết thêm hoặc sửa đổi Unit Test.
>   * `docs`: Sửa đổi tài liệu hướng dẫn (README.md, API doc).

## 2. GitHub Actions CI/CD

> **🔍 WHAT:** GitHub Actions là CI/CD platform tích hợp trong GitHub – tự động chạy workflows (test, build, deploy) khi có event (push, PR, schedule) theo cấu hình YAML trong `.github/workflows/`.
>
> **💡 WHY:** Tự động hóa loại bỏ human error khi deploy. Không cần nhớ build lại hay chạy test trước deploy. PR không pass test không thể merge – enforced quality gate. Deploy tự động sau merge vào main.
>
> **⚙️ HOW:** Workflow file YAML định nghĩa: `on` (trigger event), `jobs` (parallel), `steps` (tuần tự). GitHub cung cấp runner miễn phí (Ubuntu, Windows, macOS). `secrets` store sensitive values (password, token).
>
> **📍 WHEN/WHERE:** Trigger trên push vào main/dev, tạo PR. CI job: checkout → build → test → report coverage. CD job (chỉ khi merge main): build Docker image → push registry → SSH vào server và redeploy.

```yaml
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  # JOB 1: CI – Build & Test
  build-and-test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: testdb
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready
          --health-interval 10s

    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Cache Maven dependencies
        uses: actions/cache@v3
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}

      - name: Build & Test
        run: mvn -B verify
        env:
          SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/testdb
          SPRING_DATASOURCE_USERNAME: test
          SPRING_DATASOURCE_PASSWORD: test

      - name: Upload test report
        uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: test-reports
          path: target/surefire-reports/

  # JOB 2: CD – Build Docker & Deploy (chỉ khi push vào main)
  deploy:
    runs-on: ubuntu-latest
    needs: build-and-test   # chạy sau khi CI pass
    if: github.ref == 'refs/heads/main'

    steps:
      - uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build & Push Docker Image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp:latest
            ${{ secrets.DOCKERHUB_USERNAME }}/myapp:${{ github.sha }}

      - name: Deploy to VPS
        uses: appleboy/ssh-action@v1.0.0
        with:
          host: ${{ secrets.VPS_HOST }}
          username: ${{ secrets.VPS_USER }}
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /opt/myapp
            docker-compose pull
            docker-compose up -d --no-deps app
            docker image prune -f
```

> **📝 Giải thích chi tiết mã cấu hình GitHub Actions:**
> * `on`: Khai báo các sự kiện (triggers) kích hoạt pipeline tự động. Ở đây pipeline tự động chạy bất kỳ khi nào có thao tác `push` code lên nhánh `main`, `develop` hoặc khi có một Pull Request mở nhắm vào nhánh `main`.
> * `runs-on: ubuntu-latest`: Chỉ định hệ điều hành của máy ảo chạy pipeline (Runner) do GitHub cấp phát miễn phí.
> * `services.postgres`: Khởi tạo một container PostgreSQL ảo chạy ngầm song song với máy ảo build code để phục vụ riêng cho tầng Integration Test chạy thử (không cần mock DB).
> * `actions/checkout@v4`: Action chuẩn của GitHub để tải (clone) mã nguồn dự án từ kho chứa Git vào môi trường máy ảo để build.
> * `actions/cache@v3`: Bật cơ chế bộ nhớ đệm (Cache) cho các thư viện Maven. Nó dựa trên mã băm của file `pom.xml` để lưu trữ thư mục `~/.m2`. Ở các lần chạy tiếp theo, máy ảo chỉ cần bung nén cache ra dùng chứ không cần tải lại toàn bộ thư viện, giúp tăng tốc pipeline cực nhanh.
> * `mvn -B verify`: Lệnh Maven chạy biên dịch và thực thi toàn bộ các Unit Test và Integration Test của dự án ở chế độ Batch mode (`-B` không in chi tiết dài dòng).
> * `if: failure()`: Điều kiện chạy có điều kiện. Nếu bước build/test trước đó bị thất bại, Action này sẽ chạy để tự động nén và tải lên kho chứa (Upload Artifact) các tệp tin báo cáo lỗi chi tiết của JUnit (`target/surefire-reports/`) để lập trình viên tải về gỡ lỗi.
> * `needs: build-and-test`: Ràng buộc thứ tự chạy. Job CD `deploy` chỉ được phép bắt đầu chạy sau khi Job CI `build-and-test` đã chạy qua thành công trơn tru.
> * `if: github.ref == ...`: Ràng buộc bảo mật. Chỉ thực hiện Deploy lên Server thật khi sự kiện xảy ra trên nhánh chính `main` (không deploy khi push code lên nhánh phát triển `develop` hoặc trên PR).
> * `docker/build-push-action`: Biên dịch Dockerfile của dự án thành image và tự động đẩy (push) lên kho lưu trữ Docker Hub. Tag image được đánh dấu bằng `github.sha` (Mã băm commit của git) giúp ta có lịch sử các bản deploy rõ ràng, hỗ trợ rollback về bất kỳ version cũ nào khi có sự cố.
> * `appleboy/ssh-action`: Tự động tạo kết nối SSH bảo mật trực tiếp vào VPS của bạn để thực thi các dòng lệnh Deploy ngầm:
>   * `docker-compose pull`: Tải ảnh Docker Image mới nhất vừa build về VPS.
>   * `docker-compose up -d --no-deps app`: Khởi động lại duy nhất service `app` để áp dụng bản cập nhật mới mà hoàn toàn **không làm gián đoạn hay khởi động lại các container DB/Redis đang chạy**.
>   * `docker image prune -f`: Dọn dẹp và xóa bỏ các ảnh Docker Image cũ bị treo (dangling images) để tránh làm đầy ổ cứng VPS theo thời gian.

## 3. GitHub Secrets

> **🔍 WHAT:** GitHub Secrets là encrypted key-value storage cho sensitive data (passwords, API keys, SSH keys) dùng trong GitHub Actions workflows – không lộ trong code hay logs.
>
> **💡 WHY:** Hardcode credentials trong code là security vulnerability nghiêm trọng. Secrets được mã hóa, chỉ accessible trong workflow runtime, không hiển thị trong logs. Khác nhau giữa environment (dev/prod).
>
> **⚙️ HOW:** Settings → Secrets → Actions → New repository secret. Trong workflow tham chiếu bằng `${{ secrets.MY_SECRET }}`. Environment secrets scope vào specific deployment environment.
>
> **📍 WHEN/WHERE:** Mọi credentials dùng trong CI/CD: Docker Hub token, VPS SSH key, database password, JWT secret, AWS keys. Không bao giờ commit .env file có credentials vào Git.

```bash
# .gitignore – luôn thêm để không commit credentials
.env
.env.local
.env.production
*.pem
*.key
application-prod.yml
```

> **📝 Giải thích chi tiết bảo mật Secrets:**
> * **Nguyên tắc an toàn**: Toàn bộ các thông tin nhạy cảm (Private Key, Password DB, Secret key) phải được đưa vào **GitHub Secrets**. Spring Boot và Docker Compose sẽ cấu hình đọc thông tin qua biến môi trường.
> * `.gitignore`: Khai báo danh sách các file cấu hình và khóa bí mật cá nhân tuyệt đối **không bao giờ được phép đưa lên GitHub**. Nếu lỡ commit private key hay password lên GitHub (kể cả Repo Private), bạn bắt buộc phải thu hồi và đổi khóa mới ngay lập tức vì các robot dò quét thông tin có mặt ở khắp nơi!

## 4. Monitoring & Logging

> **🔍 WHAT:** Monitoring thu thập và visualize metrics theo thời gian thực (Prometheus + Grafana). Logging ghi lại events với context đầy đủ (SLF4J + Logback → ELK Stack hoặc CloudWatch).
>
> **💡 WHY:** Không có monitoring = không biết hệ thống đang hoạt động thế nào. Không có logging = không debug được khi có lỗi production. "You can't improve what you don't measure".
>
> **⚙️ HOW:** Prometheus scrape metrics từ `/actuator/prometheus` mỗi 15s, lưu time-series data. Grafana query Prometheus để vẽ dashboard. Log với structured format (JSON) để dễ parse và search.
>
> **📍 WHEN/WHERE:** Bắt buộc trong production. Tạo dashboard: request rate, error rate, latency p95, JVM memory, DB connection pool. Alert khi: error rate > 5%, latency > 2s, disk > 80%, service down.

```yaml
# docker-compose-monitoring.yml
services:
  prometheus:
    image: prom/prometheus:latest
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
    ports: ["9090:9090"]

  grafana:
    image: grafana/grafana:latest
    environment:
      GF_SECURITY_ADMIN_PASSWORD: admin
    ports: ["3000:3000"]
    volumes:
      - grafana_data:/var/lib/grafana
```

```yaml
# prometheus.yml
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: 'spring-boot-app'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['app:8080']
```

```java
// Structured logging với SLF4J + MDC
@RestControllerAdvice
@Slf4j
public class RequestLoggingFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) request;
        String requestId = UUID.randomUUID().toString();

        MDC.put("requestId", requestId);
        MDC.put("method", req.getMethod());
        MDC.put("path", req.getRequestURI());

        long start = System.currentTimeMillis();
        try {
            chain.doFilter(request, response);
        } finally {
            long duration = System.currentTimeMillis() - start;
            MDC.put("duration", String.valueOf(duration));
            log.info("Request completed"); // JSON log với context đầy đủ
            MDC.clear();
        }
    }
}
```

> **📝 Giải thích chi tiết code Monitoring và Logging:**
> * `scrape_interval: 15s`: Prometheus định kỳ cứ mỗi 15 giây sẽ gửi request tới endpoint `/actuator/prometheus` của ứng dụng Spring Boot để thu thập dữ liệu hiệu năng (Metrics) dạng Time-series.
> * `MDC (Mapped Diagnostic Context)`: Lớp tiện ích cực mạnh của SLF4J/Logback. Nó cho phép ta đính kèm các trường thông tin tùy biến (như `requestId` sinh ra ngẫu nhiên cho mỗi request, phương thức HTTP, đường dẫn URL, thời gian thực thi hàm...) vào **Ngữ cảnh ghi log**. Khi bạn gọi `log.info()`, toàn bộ các thông tin đính kèm trong MDC sẽ tự động được ghi nhận ra dưới dạng cấu trúc **JSON log**. Kỹ thuật này giúp các hệ thống log trung tâm (như ELK, Splunk) dễ dàng lọc, tìm kiếm và xâu chuỗi toàn bộ quá trình xử lý của một request đơn lẻ qua Trace ID.

## 5. Code Quality – SonarQube

> **🔍 WHAT:** SonarQube là platform phân tích code tĩnh – phát hiện bugs tiềm ẩn, security vulnerabilities, code smells, code duplication và đo test coverage trong codebase.
>
> **💡 WHY:** Code review thủ công bỏ sót nhiều loại lỗi. SonarQube phân tích tự động, enforces quality gate (reject merge nếu quality score thấp), theo dõi technical debt theo thời gian.
>
> **⚙️ HOW:** Chạy SonarQube server (Docker), cấu hình project, integrate với Maven (`mvn sonar:sonar`). Thêm SonarCloud vào GitHub Actions để analyze mỗi PR. Quality Gate định nghĩa ngưỡng chấp nhận được.
>
> **📍 WHEN/WHERE:** Integrate vào CI pipeline – chạy SonarQube analysis sau khi test. Block merge PR nếu Quality Gate fail. Dashboard cho tech lead xem technical debt của toàn dự án.

```yaml
# GitHub Actions: add SonarCloud step
- name: Analyze with SonarCloud
  uses: SonarSource/sonarcloud-github-action@master
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  with:
    args: >
      -Dsonar.projectKey=my-project
      -Dsonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
```

> **📝 Giải thích chi tiết cấu hình SonarQube:**
> * `sonar.coverage.jacoco.xmlReportPaths`: Trỏ đường dẫn trực tiếp tới file báo cáo độ phủ kiểm thử XML do Jacoco sinh ra. SonarQube sẽ kết hợp phân tích tĩnh dòng code và đối chiếu với dữ liệu kiểm thử để cảnh báo trực quan các vùng code logic nhạy cảm nào đang bị "bỏ quên" chưa viết test trên giao diện dashboard.

## 6. Infrastructure as Code – Terraform (cơ bản)

> **🔍 WHAT:** Terraform là tool IaC (Infrastructure as Code) – định nghĩa infrastructure (VPS, database, network, DNS) bằng code HCL, apply để tự động tạo/thay đổi trên cloud provider.
>
> **💡 WHY:** Click tay trên console không reproducible, không versionable. Terraform giúp: tạo environment mới trong vài phút, track thay đổi infrastructure qua Git, destroy và recreate infrastructure dễ dàng.
>
> **⚙️ HOW:** Viết `.tf` files định nghĩa resources. `terraform init` tải providers. `terraform plan` xem thay đổi trước khi apply. `terraform apply` tạo/thay đổi infrastructure. State file theo dõi resources đang tồn tại.
>
> **📍 WHEN/WHERE:** Khi cần tạo lại environment (staging, disaster recovery). Trong CI/CD để auto-provision infrastructure. Level DevOps/Senior Backend – không bắt buộc cho Junior nhưng là điểm cộng lớn.

```hcl
# main.tf – tạo VPS trên DigitalOcean
terraform {
  required_providers {
    digitalocean = { source = "digitalocean/digitalocean" }
  }
}

provider "digitalocean" {
  token = var.do_token
}

resource "digitalocean_droplet" "app_server" {
  image    = "ubuntu-22-04-x64"
  name     = "myapp-production"
  region   = "sgp1"
  size     = "s-2vcpu-2gb"
  ssh_keys = [data.digitalocean_ssh_key.default.id]

  user_data = file("cloud-init.sh")  # tự động chạy script cài Docker
}

output "server_ip" {
  value = digitalocean_droplet.app_server.ipv4_address
}
```

```bash
terraform init
terraform plan -var="do_token=$DO_TOKEN"
terraform apply -auto-approve
terraform destroy  # dọn dẹp sạch tài nguyên VPS
```

> **📝 Giải thích chi tiết code và lệnh Terraform:**
> * `resource "digitalocean_droplet" "app_server"`: Khai báo tài nguyên phần cứng (ở đây là một VPS Droplet chạy hệ điều hành Ubuntu 22.04, đặt tại khu vực Singapore `sgp1`, cấu hình 2 vCPU và 2GB RAM).
> * `user_data`: Khai báo script chạy tự động ngay lúc VPS vừa được khởi tạo thành công (thường dùng để viết script tự động cài đặt Docker, Git chuẩn bị môi trường).
> * `terraform init`: Khởi tạo môi trường Terraform, tự động tải các plugin Provider kết nối tương ứng của nhà cung cấp cloud (ở đây là DigitalOcean).
> * `terraform plan`: Phân tích và in ra màn hình console chi tiết các tài nguyên nào sẽ được tạo mới (`+`), sửa đổi (`~`) hoặc xóa bỏ (`-`). Đây là bước kiểm tra an toàn vô cùng quan trọng trước khi chạy thật.
> * `terraform apply`: Tiến hành gọi API lên Cloud Provider để thực sự tạo tài nguyên và trả ra địa chỉ IP vật lý của VPS ở phần Output.
> * `terraform destroy`: Lệnh dọn dẹp (xóa sạch) toàn bộ hạ tầng đã tạo ở file cấu hình để tránh bị tính phí tiền mây vô ích khi không còn nhu cầu sử dụng.
