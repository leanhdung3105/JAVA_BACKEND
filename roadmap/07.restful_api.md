# 07. RESTful API với Spring Boot

> **Mục tiêu:** Xây dựng RESTful API chuẩn, có validation, error handling và documentation.

---

## 1. REST Principles

> **🔍 WHAT:** REST (Representational State Transfer) là kiến trúc thiết kế API dùng HTTP protocol, mỗi resource có URI riêng và dùng HTTP methods (GET/POST/PUT/DELETE) đúng ngữ nghĩa.
>
> **💡 WHY:** API tuân theo REST conventions giúp frontend/mobile developer dễ đoán và dùng, giảm tài liệu cần viết, tương thích với mọi HTTP client (browser, Postman, curl, mobile app).
>
> **⚙️ HOW:** Thiết kế URI là danh từ số nhiều (`/users`, `/orders`), dùng HTTP method đúng (GET=read, POST=create, PUT/PATCH=update, DELETE=delete), trả về HTTP status code chính xác (200, 201, 404, 422...).
>
> **📍 WHEN/WHERE:** Áp dụng khi thiết kế mọi API endpoint trong Controller. Là giao ước giữa backend và frontend – cần thống nhất trước khi code.

| Method | Dùng cho | Status thành công |
|--------|---------|-------------------|
| `GET` | Đọc dữ liệu | 200 OK |
| `POST` | Tạo mới | 201 Created |
| `PUT` | Cập nhật toàn bộ | 200 OK |
| `PATCH` | Cập nhật một phần | 200 OK |
| `DELETE` | Xóa | 204 No Content |

| Code | Ý nghĩa |
|------|---------|
| `400 Bad Request` | Request không hợp lệ |
| `401 Unauthorized` | Chưa xác thực |
| `403 Forbidden` | Không có quyền |
| `404 Not Found` | Không tìm thấy |
| `409 Conflict` | Xung đột (email đã tồn tại) |
| `422 Unprocessable Entity` | Validation error |
| `500 Internal Server Error` | Lỗi server |

## 2. Xây dựng REST Controller

> **🔍 WHAT:** `@RestController` là class xử lý HTTP request, mapping URL với method handler, nhận input từ request và trả response – là tầng ngoài cùng của ứng dụng Spring Boot.
>
> **💡 WHY:** Tách biệt HTTP concerns (parsing request, setting status code, serialization) khỏi business logic. Controller chỉ điều phối, không chứa logic – giúp code clean và dễ test.
>
> **⚙️ HOW:** Dùng `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` để map URL. `@PathVariable` lấy từ URL path, `@RequestParam` từ query string, `@RequestBody` từ request body. Trả `ResponseEntity<T>` để kiểm soát status code.
>
> **📍 WHEN/WHERE:** Mỗi resource (User, Order, Product) có 1 Controller riêng. Controller KHÔNG gọi Repository trực tiếp – phải qua Service. Validate input ngay tại Controller với `@Valid`.

```java
@RestController
@RequestMapping("/api/v1/users")
@RequiredArgsConstructor
public class UserController {
    private final UserService userService;

    // GET /api/v1/users?page=0&size=10
    @GetMapping
    public ResponseEntity<Page<UserResponse>> getAllUsers(
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "10") int size
    ) {
        Pageable pageable = PageRequest.of(page, size);
        return ResponseEntity.ok(userService.getAllUsers(pageable));
    }

    // GET /api/v1/users/{id}
    @GetMapping("/{id}")
    public ResponseEntity<UserResponse> getUserById(@PathVariable Long id) {
        return ResponseEntity.ok(userService.getUserById(id));
    }

    // POST /api/v1/users
    @PostMapping
    public ResponseEntity<UserResponse> createUser(@RequestBody @Valid CreateUserRequest request) {
        UserResponse response = userService.createUser(request);
        URI location = URI.create("/api/v1/users/" + response.getId());
        return ResponseEntity.created(location).body(response);
    }

    // PUT /api/v1/users/{id}
    @PutMapping("/{id}")
    public ResponseEntity<UserResponse> updateUser(
        @PathVariable Long id,
        @RequestBody @Valid UpdateUserRequest request
    ) {
        return ResponseEntity.ok(userService.updateUser(id, request));
    }

    // DELETE /api/v1/users/{id}
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteUser(@PathVariable Long id) {
        userService.deleteUser(id);
        return ResponseEntity.noContent().build();
    }
}
```

> **📝 Giải thích chi tiết code Controller:**
> * `@RequestMapping("/api/v1/users")`: Thiết lập tiền tố URL chung cho toàn bộ các endpoint xử lý trong Controller này. Đánh dấu versioning dạng `/v1/` là best practice giúp dễ bảo trì và nâng cấp API sau này mà không làm gián đoạn frontend chạy version cũ.
> * `@RequestParam(defaultValue = "0") int page`: Đọc các biến tham số dạng truy vấn (Query Parameters) từ thanh URL (ví dụ: `?page=2`). Nếu client không truyền, hệ thống sẽ sử dụng giá trị mặc định là `"0"`.
> * `@PathVariable Long id`: Ánh xạ trực tiếp phần giá trị động biến đổi trên đường dẫn URL (như `/users/42`) vào biến `id` của phương thức.
> * `@RequestBody @Valid CreateUserRequest`:
>   * `@RequestBody`: Chỉ thị cho Spring chuyển đổi trực tiếp định dạng chuỗi JSON thô nhận từ Body của HTTP Request sang đối tượng DTO của Java tương ứng.
>   * `@Valid`: Kích hoạt cơ chế kiểm tra tính hợp lệ của dữ liệu (Validation) dựa trên các ràng buộc được khai báo trong class DTO. Nếu dữ liệu sai, request sẽ bị chặn đứng ngay tại đây và trả lỗi về client mà không cần chạy code vào Service.
> * `ResponseEntity.ok(...)`: Tạo phản hồi HTTP Response thành công có trạng thái Status Code là `200 OK`, đính kèm dữ liệu DTO ở phần body.
> * `ResponseEntity.created(location).body(...)`: Tạo phản hồi tạo mới dữ liệu thành công có trạng thái Status Code là `21 Created`. Phần Header sẽ đính kèm địa chỉ đường dẫn truy cập tài nguyên vừa tạo (`location`), đồng thời trả về object vừa tạo ở body.
> * `ResponseEntity.noContent().build()`: Tạo phản hồi xóa thành công có trạng thái Status Code là `204 No Content` (không mang dữ liệu trả về ở phần body).

### DTO với validation

```java
// Request DTO
@Data
public class CreateUserRequest {
    @NotBlank(message = "Email không được để trống")
    @Email(message = "Email không hợp lệ")
    private String email;

    @NotBlank
    @Size(min = 2, max = 100)
    private String fullName;

    @NotBlank
    @Size(min = 8, message = "Mật khẩu phải ít nhất 8 ký tự")
    @Pattern(regexp = ".*[A-Z].*", message = "Phải có ít nhất 1 chữ hoa")
    private String password;
}

// Response DTO (không trả password)
@Data @Builder
public class UserResponse {
    private Long id;
    private String email;
    private String fullName;
    private boolean active;
    private LocalDateTime createdAt;
}
```

> **📝 Giải thích chi tiết code:**
> * **DTO (Data Transfer Object)**: Lớp trung gian dùng để truyền tải dữ liệu. Tuyệt đối không nên phơi bày trực tiếp cấu trúc Entity của Database ra ngoài API vì lý do bảo mật và tính toàn vẹn hệ thống. Việc tách biệt `CreateUserRequest` (nhận dữ liệu tạo mới) và `UserResponse` (dữ liệu trả ra) giúp lọc bỏ các trường nhạy cảm (như `password` hay trường quản lý nội bộ).
> * `@NotBlank`: Ràng buộc bắt buộc trường dữ liệu không được phép mang giá trị `null` và không được chứa toàn khoảng trắng (`""` hoặc `"   "`).
> * `@Email`: Ràng buộc kiểm tra định dạng email hợp lệ dựa trên cấu trúc Regex chuẩn.
> * `@Size(min = 8)`: Ràng buộc kiểm tra độ dài chuỗi ký tự tối thiểu.
> * `@Pattern(regexp = "...")`: Ràng buộc kiểm tra tính hợp lệ của chuỗi ký tự thông qua biểu thức chính quy (Regular Expression - Regex).

## 3. Global Exception Handler

> **🔍 WHAT:** `@RestControllerAdvice` là class xử lý exception tập trung cho toàn bộ ứng dụng – thay vì try-catch trong mỗi controller, exception được bắt và format ở một nơi duy nhất.
>
> **💡 WHY:** Nếu mỗi controller tự xử lý exception, response error sẽ không nhất quán, code lặp nhiều. Global handler đảm bảo mọi error đều có format chuẩn và đúng HTTP status code.
>
> **⚙️ HOW:** Tạo class `@RestControllerAdvice`, các method `@ExceptionHandler(XxxException.class)` nhận exception và trả `ResponseEntity<ErrorResponse>` với status code phù hợp.
>
> **📍 WHEN/WHERE:** Bắt buộc trong mọi dự án Spring Boot. Đặt trong package `exception/`. Xử lý: custom business exceptions (404, 409), validation exception (422), security exception (401/403), và catch-all 500.

```java
// Standard error response DTO
@Data @Builder
public class ErrorResponse {
    private int status;
    private String error;
    private String message;
    private LocalDateTime timestamp;
    private Map<String, String> fieldErrors; // cho validation errors
}

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(ErrorResponse.builder()
                .status(404).error("Not Found")
                .message(ex.getMessage())
                .timestamp(LocalDateTime.now())
                .build());
    }

    // Validation errors
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors()
            .forEach(err -> errors.put(err.getField(), err.getDefaultMessage()));

        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
            .body(ErrorResponse.builder()
                .status(422).error("Validation Failed")
                .message("Dữ liệu không hợp lệ")
                .fieldErrors(errors)
                .timestamp(LocalDateTime.now())
                .build());
    }

    // Catch-all
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGeneral(Exception ex) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(ErrorResponse.builder()
                .status(500).error("Internal Server Error")
                .message("Đã có lỗi xảy ra, vui lòng thử lại sau")
                .timestamp(LocalDateTime.now())
                .build());
    }
}
```

> **📝 Giải thích chi tiết code Exception Handling:**
> * `@RestControllerAdvice`: Đánh dấu class là trung tâm bắt lỗi tập trung của ứng dụng (AOP). Nó chặn bắt toàn bộ các ngoại lệ (Exception) phát ra từ tầng Controller của bất kỳ class nào trong hệ thống.
> * `@ExceptionHandler(ResourceNotFoundException.class)`: Khai báo phương thức chịu trách nhiệm xử lý khi xảy ra ngoại lệ `ResourceNotFoundException`. Spring sẽ truyền đối tượng exception cụ thể vào tham số `ex` để ta lấy ra message giải thích lỗi.
> * `MethodArgumentNotValidException`: Ngoại lệ mặc định của Spring Boot được ném ra khi validation một DTO (được gắn cờ `@Valid`) bị thất bại.
> * `ex.getBindingResult().getFieldErrors()`: Phương thức truy xuất sâu vào kết quả validation của Spring để lấy ra danh sách chi tiết các trường bị lỗi, từ đó bóc tách ra tên trường bị sai (`err.getField()`) cùng thông điệp lỗi tương ứng để đóng gói trả ra cho client sửa đổi.
> * `handleGeneral(Exception ex)`: Phương thức bắt lỗi generic cao nhất (`Exception.class`). Nó đóng vai trò là "màng lọc an toàn cuối cùng". Nếu hệ thống xảy ra các lỗi kỹ thuật không lường trước (như lỗi kết nối DB, lỗi tràn bộ nhớ), nó sẽ trả ra mã lỗi `500` chung chung và thông điệp an toàn, tránh để lộ cấu trúc code nội bộ (stack trace) ra ngoài giao diện người dùng để ngăn ngừa rủi ro bảo mật.

## 4. Response Wrapper (chuẩn hóa response)

> **🔍 WHAT:** ApiResponse wrapper là class bọc ngoài mọi response, đảm bảo mọi API trả về cùng một structure với `success`, `message`, `data` và `timestamp` – dù là thành công hay lỗi.
>
> **💡 WHY:** Frontend dễ xử lý hơn khi response luôn có structure nhất quán. Không phải kiểm tra tùy từng API xem data ở đâu. Dễ thêm metadata (total count, pagination info) mà không breaking change.
>
> **⚙️ HOW:** Tạo generic class `ApiResponse<T>` với factory methods `success()` và `error()`. Wrap tất cả return value trong controller. Có thể dùng `@ControllerAdvice` + `ResponseBodyAdvice` để tự động wrap.
>
> **📍 WHEN/WHERE:** Áp dụng nhất quán cho toàn bộ API trong dự án. Thống nhất với frontend team về format trước khi implement. Không áp dụng cho file download endpoint.

```java
@Data @Builder
public class ApiResponse<T> {
    private boolean success;
    private String message;
    private T data;
    private LocalDateTime timestamp;

    public static <T> ApiResponse<T> success(T data) {
        return ApiResponse.<T>builder()
            .success(true).data(data)
            .timestamp(LocalDateTime.now()).build();
    }

    public static <T> ApiResponse<T> success(String message, T data) {
        return ApiResponse.<T>builder()
            .success(true).message(message).data(data)
            .timestamp(LocalDateTime.now()).build();
    }
}

// Sử dụng trong controller
@GetMapping("/{id}")
public ResponseEntity<ApiResponse<UserResponse>> getUser(@PathVariable Long id) {
    return ResponseEntity.ok(ApiResponse.success(userService.getUserById(id)));
}
```

> **📝 Giải thích chi tiết code:**
> * `public class ApiResponse<T>`: Lớp Generic bọc ngoài. Kiểu dữ liệu `T` của trường `data` sẽ tự động biến động tùy thuộc vào kiểu dữ liệu thực tế mà API trả ra (ví dụ: `UserResponse` hoặc danh sách `List<ProductResponse>`).
> * `ApiResponse.<T>builder()`: Sử dụng mẫu thiết kế **Builder Pattern** của Lombok để khởi tạo đối tượng `ApiResponse` một cách tường minh và trơn tru.

## 5. API Documentation với Swagger/OpenAPI

> **🔍 WHAT:** Swagger/OpenAPI là tiêu chuẩn mô tả REST API. Springdoc-openapi tự động generate interactive documentation từ code annotations, accessible qua browser.
>
> **💡 WHY:** Tài liệu API luôn up-to-date với code (không phải viết tay). Frontend, mobile developer và QA đều dùng Swagger UI để khám phá và test API mà không cần Postman setup thủ công.
>
> **⚙️ HOW:** Thêm `springdoc-openapi-starter-webmvc-ui` dependency, Spring Boot tự expose `/swagger-ui` và `/api-docs`. Thêm `@Operation`, `@ApiResponse`, `@Tag` để enrichment documentation.
>
> **📍 WHEN/WHERE:** Enabled mặc định trong `dev` profile, disable hoặc restrict trong `prod`. Share Swagger UI URL với team frontend thay vì viết API doc thủ công. CI/CD có thể auto-generate API spec file.

```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.3.0</version>
</dependency>
```

```java
@RestController
@Tag(name = "Users", description = "User management endpoints")
public class UserController {

    @Operation(summary = "Tạo người dùng mới")
    @ApiResponses({
        @ApiResponse(responseCode = "201", description = "Tạo thành công"),
        @ApiResponse(responseCode = "409", description = "Email đã tồn tại"),
        @ApiResponse(responseCode = "422", description = "Dữ liệu không hợp lệ")
    })
    @PostMapping
    public ResponseEntity<UserResponse> createUser(@RequestBody @Valid CreateUserRequest request) {
        // ...
    }
}
// Truy cập: http://localhost:8080/swagger-ui/index.html
```

> **📝 Giải thích chi tiết code:**
> * `springdoc-openapi-starter-webmvc-ui`: Thư viện tích hợp OpenAPI 3 và giao diện Swagger UI đẹp đẽ vào dự án Spring Boot 3.
> * `@Tag(name = "Users")`: Gom nhóm các endpoint của Controller này vào một khu vực riêng biệt có tiêu đề là "Users" trên giao diện Swagger UI.
> * `@Operation(summary = "...")`: Định nghĩa mô tả ngắn gọn về chức năng của API để các lập trình viên frontend hoặc kiểm thử viên hiểu ngay nghiệp vụ của endpoint.
> * `@ApiResponses`: Khai báo danh sách các trường hợp mã trạng thái (HTTP Status Code) và mô tả tương ứng mà API này có khả năng trả về, giúp Swagger UI hiển thị tài liệu hướng dẫn cực kỳ trực quan và cho phép chạy test trực tiếp ngay trên trình duyệt (Try it out).

## 6. CORS Configuration

> **🔍 WHAT:** CORS (Cross-Origin Resource Sharing) là cơ chế browser cho phép/từ chối request từ domain khác. Nếu frontend ở `localhost:3000` gọi API ở `localhost:8080`, browser sẽ block trừ khi backend cấu hình CORS.
>
> **💡 WHY:** Bảo mật browser ngăn script từ website A tự do gọi API của website B. Backend cần khai báo rõ những origin nào được phép để frontend app hoạt động đúng.
>
> **⚙️ HOW:** Tạo `CorsConfigurationSource` bean trong Spring Security config. Cấu hình allowed origins, methods, headers. `AllowCredentials(true)` cần thiết khi dùng cookie/session.
>
> **📍 WHEN/WHERE:** Cần cấu hình khi frontend và backend chạy trên port/domain khác nhau – luôn xảy ra trong development (React :3000 + Spring :8080) và production (app.example.com + api.example.com).

```java
@Configuration
public class CorsConfig {
    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of(
            "http://localhost:3000",
            "https://myapp.com"
        ));
        config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
        config.setAllowedHeaders(List.of("*"));
        config.setAllowCredentials(true);
        config.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", config);
        return source;
    }
}
```

> **📝 Giải thích chi tiết code:**
> * `setAllowedOrigins(...)`: Khai báo danh sách các địa chỉ Domain (Origin) của Frontend được quyền gửi yêu cầu HTTP tới Server Backend. Tránh dùng dấu sao `*` trên môi trường Production để ngăn ngừa rủi ro bảo mật.
> * `setAllowedMethods(...)`: Danh sách các phương thức HTTP cho phép client sử dụng. Phương thức `OPTIONS` là bắt buộc vì trình duyệt luôn tự động gửi trước một request rỗng (Preflight Request) để kiểm tra CORS cấu hình trước khi gửi request thật.
> * `setAllowedHeaders(List.of("*"))`: Cho phép mọi Header tùy biến từ Client gửi lên (như `Authorization` mang JWT token).
> * `setAllowCredentials(true)`: Cấu hình cho phép client gửi kèm cookie hoặc thông tin xác thực HTTP Authentication trong request. **Lưu ý:** Khi bật cấu hình này, `allowedOrigins` bắt buộc phải khai báo domain cụ thể chứ không được phép cấu hình wildcard `*`.
> * `setMaxAge(3600L)`: Thời gian lưu cấu hình CORS này trong bộ nhớ cache của trình duyệt client (3600 giây = 1 giờ). Giúp giảm bớt việc trình duyệt phải liên tục gửi Preflight Request lên server trước mỗi API request, tối ưu tốc độ ứng dụng.

## 7. Pagination & Filtering

> **🔍 WHAT:** Pagination là chia kết quả query thành trang nhỏ thay vì trả toàn bộ. Filtering là lọc dữ liệu theo điều kiện động từ query parameter.
>
> **💡 WHY:** Trả 1 triệu records cùng lúc sẽ làm sập server và OOM. Pagination giới hạn lượng data mỗi request. Filtering giúp client lấy đúng dữ liệu cần, giảm transfer và xử lý ở client.
>
> **⚙️ HOW:** Spring Data JPA hỗ trợ `Pageable` interface – truyền vào repository method để tự động LIMIT/OFFSET. `JpaSpecificationExecutor` + `Specification` pattern cho dynamic filtering.
>
> **📍 WHEN/WHERE:** Bất kỳ endpoint nào trả list data: `GET /products`, `GET /users`, `GET /orders`. Luôn có pagination mặc định (size=20), có thể cho phép sort qua query param.

```java
// Controller
@GetMapping
public ResponseEntity<Page<ProductResponse>> getProducts(
    @RequestParam(defaultValue = "0") int page,
    @RequestParam(defaultValue = "20") int size,
    @RequestParam(defaultValue = "id") String sortBy,
    @RequestParam(required = false) String name,
    @RequestParam(required = false) Long categoryId
) {
    Pageable pageable = PageRequest.of(page, size, Sort.by(sortBy));
    return ResponseEntity.ok(productService.getProducts(name, categoryId, pageable));
}

// Repository hỗ trợ Specification (dynamic filtering)
@Repository
public interface ProductRepository extends JpaRepository<Product, Long>,
        JpaSpecificationExecutor<Product> {}

// Service
public Page<ProductResponse> getProducts(String name, Long categoryId, Pageable pageable) {
    Specification<Product> spec = Specification.where(null);
    if (name != null) spec = spec.and((root, q, cb) ->
        cb.like(cb.lower(root.get("name")), "%" + name.toLowerCase() + "%"));
    if (categoryId != null) spec = spec.and((root, q, cb) ->
        cb.equal(root.get("categoryId"), categoryId));
    return productRepository.findAll(spec, pageable).map(this::toResponse);
}
```

> **📝 Giải thích chi tiết code:**
> * `Pageable pageable = PageRequest.of(page, size, Sort.by(sortBy))`: Khởi tạo đối tượng phân trang và sắp xếp `Pageable` của Spring. Nó tự gom thông tin về chỉ mục trang (`page`), số phần tử mỗi trang (`size`), và cột cần sắp xếp (`sortBy`).
> * `JpaSpecificationExecutor<Product>`: Mở rộng repository để hỗ trợ cơ chế truy vấn động (JPA Criteria API) thông qua đối tượng `Specification`.
> * `Specification<Product> spec`: Xây dựng câu query lọc dữ liệu động tại thời điểm chạy dựa trên việc client có truyền tham số tìm kiếm lên hay không:
>   * `root.get("name")`: Trỏ vào thuộc tính `name` của đối tượng Entity.
>   * `cb.like(...)`: Xây dựng điều kiện so sánh chuỗi (LIKE trong SQL) kèm theo việc chuẩn hóa về dạng chữ thường (`cb.lower`) để tìm kiếm không phân biệt hoa thường.
>   * `spec.and(...)`: Kết hợp nối thêm các điều kiện lọc một cách động.
> * `productRepository.findAll(spec, pageable)`: Hibernate sẽ tự động phân tích và sinh ra câu lệnh SQL có các mệnh đề `WHERE` tương ứng với các điều kiện có trong `spec`, đồng thời tự động đính kèm mệnh đề phân trang `LIMIT` và `OFFSET` tương thích với database. Kết quả trả về là một đối tượng `Page<Product>` chứa danh sách trang kèm theo thông tin metadata hữu ích như tổng số phần tử, tổng số trang để trả về cho client.
