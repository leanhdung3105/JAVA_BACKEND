# 10. Testing trong Java Backend

> **Mục tiêu:** Viết Unit Test, Integration Test và kiểm thử API với công cụ hiện đại.

---

## 1. Testing Pyramid

> **🔍 WHAT:** Testing Pyramid là mô hình hướng dẫn phân bổ các loại test: Unit Test (nhiều, nhanh) ở đáy, Integration Test ở giữa, E2E Test (ít, chậm) ở đỉnh.
>
> **💡 WHY:** Mỗi loại test có chi phí khác nhau về thời gian chạy và độ phức tạp. Pyramid giúp cân bằng – nhiều unit test nhanh để detect lỗi sớm, ít E2E test chậm để verify flow chính. Bỏ qua test = nợ kỹ thuật nghiêm trọng.
>
> **⚙️ HOW:** Unit Test: test một class/method đơn lẻ, mock dependencies. Integration Test: test nhiều component cùng nhau (Controller + Service + DB). E2E: test full flow từ API đến DB. Tỷ lệ khuyến nghị: 70% unit / 20% integration / 10% E2E.
>
> **📍 WHEN/WHERE:** Viết test ngay khi viết code (TDD) hoặc sau khi implement feature. Unit test trong `src/test/java` mirror với source. CI pipeline chạy toàn bộ test trước khi merge/deploy.

```
        /\
       /E2E\          ← Ít, chậm (Selenium, Playwright)
      /------\
     / Integ  \       ← Vừa (Spring Boot Test, Testcontainers)
    /----------\
   / Unit Tests \     ← Nhiều, nhanh (JUnit, Mockito)
  /______________\
```

## 2. Unit Testing với JUnit 5 & Mockito

> **🔍 WHAT:** JUnit 5 là framework viết test cho Java với annotations như `@Test`, `@BeforeEach`, `@ParameterizedTest`. Mockito là thư viện tạo mock object để thay thế real dependencies trong unit test.
>
> **💡 WHY:** Unit test chạy nhanh (milliseconds), không cần DB hay server. Mock giúp test class đơn lẻ mà không phụ thuộc DB/external service – test đáng tin cậy và stable.
>
> **⚙️ HOW:** Dùng `@ExtendWith(MockitoExtension.class)`, `@Mock` tạo mock, `@InjectMocks` inject mock vào class được test. `when(...).thenReturn(...)` setup behavior, `verify(...)` kiểm tra mock được gọi đúng cách. AssertJ cho assertions rõ ràng hơn JUnit assertions.
>
> **📍 WHEN/WHERE:** Test mọi Service method với các happy path và error case. Đặc biệt quan trọng cho business logic phức tạp (tính giá, validate rule, state machine). Mục tiêu: 80%+ code coverage cho Service layer.

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    private UserRepository userRepository;

    @Mock
    private PasswordEncoder passwordEncoder;

    @InjectMocks
    private UserServiceImpl userService;

    @Test
    @DisplayName("Tạo user thành công với email mới")
    void createUser_withNewEmail_returnsUserResponse() {
        // Given (Arrange)
        CreateUserRequest request = new CreateUserRequest();
        request.setEmail("test@example.com");
        request.setFullName("Test User");
        request.setPassword("Password1!");

        User savedUser = User.builder().id(1L).email("test@example.com").fullName("Test User").build();

        when(userRepository.existsByEmail("test@example.com")).thenReturn(false);
        when(passwordEncoder.encode("Password1!")).thenReturn("hashed");
        when(userRepository.save(any(User.class))).thenReturn(savedUser);

        // When (Act)
        UserResponse response = userService.createUser(request);

        // Then (Assert)
        assertThat(response).isNotNull();
        assertThat(response.getId()).isEqualTo(1L);
        assertThat(response.getEmail()).isEqualTo("test@example.com");

        verify(userRepository, times(1)).existsByEmail("test@example.com");
        verify(userRepository, times(1)).save(any(User.class));
        verifyNoMoreInteractions(userRepository);
    }

    @Test
    void createUser_withExistingEmail_throwsException() {
        // Given
        CreateUserRequest request = new CreateUserRequest();
        request.setEmail("existing@example.com");
        when(userRepository.existsByEmail("existing@example.com")).thenReturn(true);

        // When & Then
        assertThatThrownBy(() -> userService.createUser(request))
            .isInstanceOf(EmailAlreadyExistsException.class)
            .hasMessageContaining("existing@example.com");

        verify(userRepository, never()).save(any()); // không được gọi save
    }

    @ParameterizedTest
    @CsvSource({
        "test@example.com, true",
        "notfound@test.com, false"
    })
    void existsByEmail(String email, boolean expected) {
        when(userRepository.existsByEmail(email)).thenReturn(expected);
        assertThat(userService.existsByEmail(email)).isEqualTo(expected);
    }
}
```

> **📝 Giải thích chi tiết code Unit Test:**
> * `@ExtendWith(MockitoExtension.class)`: Tích hợp thư viện Mockito vào vòng đời kiểm thử của JUnit 5. Nó chịu trách nhiệm tự động quét và khởi tạo các đối tượng giả lập (Mock).
> * `@Mock`: Khai báo tạo một đối tượng giả lập (Mock Object) cho các lớp phụ thuộc (`UserRepository`, `PasswordEncoder`). Thư viện sẽ sinh ra một proxy rỗng mà không chạy bất kỳ đoạn code thực tế nào của các class này.
> * `@InjectMocks`: Khởi tạo instance thực tế cho đối tượng cần kiểm thử (`UserServiceImpl`), đồng thời tự động tiêm (inject) các đối tượng giả lập được khai báo bằng `@Mock` phía trên vào thông qua hàm khởi tạo.
> * `when(...).thenReturn(...)`: Định nghĩa hành vi giả lập (Stubbing). Dòng này chỉ thị cho Mockito: "Khi phương thức `existsByEmail` của UserRepository được gọi với tham số `"test@example.com"`, hãy giả lập trả về kết quả là `false` mà không cần truy vấn DB thật".
> * `any(User.class)`: Trình đối khớp linh hoạt (Argument Matcher). Phương thức `save` sẽ khớp và trả về `savedUser` cho bất kỳ đối tượng `User` nào truyền vào.
> * `assertThat(...)`: Sử dụng thư viện **AssertJ** (được tích hợp sẵn trong Spring Boot Test). Cú pháp Fluent API cực kỳ rõ nghĩa và dễ đọc (như tiếng Anh tự nhiên), trực quan hơn các khẳng định `assertEquals()` truyền thống của JUnit.
> * `verify(userRepository, times(1))`: Kiểm tra hành vi (Verification). Dòng này khẳng định phương thức `existsByEmail` bắt buộc phải được gọi **đúng một lần duy nhất** trong luồng xử lý của hàm. Nếu phương thức đó không được gọi, hoặc bị gọi 2 lần, Unit Test sẽ thất bại.
> * `verifyNoMoreInteractions(...)`: Khẳng định an toàn, đảm bảo ngoài các phương thức đã được verify phía trên, không còn bất kỳ phương thức nào khác của `userRepository` bị gọi thêm nữa trong suốt luồng chạy của hàm.
> * `assertThatThrownBy(...)`: Kiểm tra các kịch bản ngoại lệ (Error Cases). Dòng lệnh kiểm tra xem đoạn code Lambda trong `Act` có ném ra đúng ngoại lệ `EmailAlreadyExistsException` hay không, và kiểm tra thông điệp lỗi chứa trong ngoại lệ đó.
> * `@ParameterizedTest` + `@CsvSource`: Kỹ thuật **Kiểm thử tham số hóa**. Nó cho phép ta chạy một kịch bản test nhiều lần với danh sách dữ liệu đầu vào và kết quả mong muốn (`expected`) khác nhau được định nghĩa dưới dạng CSV. Giúp tránh việc phải viết nhiều phương thức test trùng lặp logic, tối ưu hóa code test sạch sẽ.

## 3. Integration Testing

> **🔍 WHAT:** Integration Test kiểm tra nhiều component thực sự làm việc cùng nhau – Controller xử lý HTTP request, Service thực thi business logic, và thường có cả DB (real hoặc in-memory).
>
> **💡 WHY:** Unit test chứng minh từng class hoạt động đúng nhưng không verify sự phối hợp giữa chúng. Integration test phát hiện các vấn đề về wiring, configuration, serialization/deserialization.
>
> **⚙️ HOW:** `@SpringBootTest` load full application context. `MockMvc` simulate HTTP requests mà không cần start server thật. `@WebMvcTest` chỉ load web layer (nhanh hơn @SpringBootTest). `@MockBean` thay mock vào Spring context.
>
> **📍 WHEN/WHERE:** Test Controller endpoints đầu đủ flow: gửi request, kiểm tra status code, response body, validate error cases. Chạy trên CI pipeline – chậm hơn unit test nhưng bắt được nhiều loại lỗi hơn.

```java
// @WebMvcTest – chỉ load web layer, nhanh
@WebMvcTest(UserController.class)
class UserControllerMvcTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private UserService userService;  // mock service, không load thật

    @Autowired
    private ObjectMapper objectMapper;

    @Test
    void getUser_existingId_returns200() throws Exception {
        UserResponse mockResponse = UserResponse.builder()
            .id(1L).email("test@example.com").fullName("Test").build();
        when(userService.getUserById(1L)).thenReturn(mockResponse);

        mockMvc.perform(get("/api/v1/users/1")
                .contentType(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.id").value(1))
            .andExpect(jsonPath("$.email").value("test@example.com"));
    }

    @Test
    void createUser_invalidEmail_returns422() throws Exception {
        CreateUserRequest request = new CreateUserRequest();
        request.setEmail("invalid-email"); // không đúng format
        request.setPassword("Password1!");
        request.setFullName("Test");

        mockMvc.perform(post("/api/v1/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isUnprocessableEntity())
            .andExpect(jsonPath("$.fieldErrors.email").exists());
    }
}
```

> **📝 Giải thích chi tiết code Integration Test:**
> * `@WebMvcTest(UserController.class)`: Chỉ định cho Spring Boot Test **chỉ khởi tạo tầng Web (Controller) và các cấu hình MVC liên quan** để tối ưu hóa tốc độ chạy test (tránh việc load toàn bộ DB, JPA, Security không liên quan).
> * `MockMvc`: Công cụ giả lập gửi yêu cầu HTTP cực mạnh. Nó cho phép ta giả lập gửi các HTTP Request (GET, POST, PUT, DELETE) trực tiếp tới các endpoint và kiểm tra kết quả phản hồi của Controller một cách toàn diện mà hoàn toàn không cần khởi động thực sự một máy chủ Web Tomcat thực tế.
> * `@MockBean`: Tạo đối tượng giả lập `UserService` và **tiêm trực tiếp đối tượng này thay thế cho Bean thật** bên trong Ngữ cảnh ứng dụng (Application Context) đang chạy của Spring.
> * `mockMvc.perform(get(...))`: Giả lập một HTTP GET Request gửi tới URL `/api/v1/users/1`.
> * `andExpect(status().isOk())`: Khẳng định rằng phản hồi trả về từ API bắt buộc phải mang trạng thái `200 OK`.
> * `jsonPath("$.id").value(1)`: Sử dụng thư viện **JsonPath** để truy xuất sâu vào nội dung JSON trả về từ body của API. Cú pháp `$.id` trỏ tới thuộc tính `id` ở gốc JSON và khẳng định giá trị của nó phải bằng `1`.
> * `objectMapper.writeValueAsString(request)`: Chuyển đổi đối tượng Java Request DTO thành một chuỗi JSON string thô để đính kèm vào phần Body của HTTP Request khi giả lập phương thức POST tạo mới dữ liệu.

## 4. Testcontainers (Database thật)

> **🔍 WHAT:** Testcontainers là thư viện khởi chạy Docker container (PostgreSQL, Redis, Kafka...) ngay trong test – dùng database/service thật thay vì in-memory mock, gần với production nhất.
>
> **💡 WHY:** H2 in-memory database khác PostgreSQL về behavior (SQL dialect, constraints). Testcontainers cho phép test với PostgreSQL thật – test tin cậy hơn, tránh "hoạt động khi test nhưng lỗi khi production".
>
> **⚙️ HOW:** Annotate test class với `@Testcontainers`, khai báo `@Container static PostgreSQLContainer<?>`. Dùng `@DynamicPropertySource` để override datasource URL bằng URL của container vừa khởi động.
>
> **📍 WHEN/WHERE:** Dùng cho Repository test (cần DB thật để verify query), Integration test của Service cần DB. Cần Docker daemon đang chạy trên máy. Chậm hơn H2 nhưng chính xác hơn nhiều.

```java
@SpringBootTest
@Testcontainers
@ActiveProfiles("test")
class UserRepositoryTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15")
        .withDatabaseName("testdb")
        .withUsername("test")
        .withPassword("test");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private UserRepository userRepository;

    @BeforeEach
    void setUp() { userRepository.deleteAll(); }

    @Test
    void findByEmail_existingEmail_returnsUser() {
        // Given
        User user = User.builder()
            .email("test@example.com").fullName("Test")
            .password("hashed").role(Role.USER).build();
        userRepository.save(user);

        // When
        Optional<User> found = userRepository.findByEmail("test@example.com");

        // Then
        assertThat(found).isPresent();
        assertThat(found.get().getEmail()).isEqualTo("test@example.com");
    }
}
```

> **📝 Giải thích chi tiết code Testcontainers:**
> * `@SpringBootTest`: Tải toàn bộ cấu hình ngữ cảnh ứng dụng (Application Context) thật của Spring Boot để thực hiện kiểm thử tích hợp toàn diện.
> * `@Testcontainers`: Bật tính năng tích hợp thư viện Testcontainers cho phép quét và tự động quản lý vòng đời của các Docker Container trong JUnit 5.
> * `@Container static PostgreSQLContainer<?>`: Khai báo yêu cầu Testcontainers tự động tải và khởi chạy một container Docker chạy PostgreSQL phiên bản 15 chính thức.
> * `@DynamicPropertySource`: Cơ chế cấu hình động tuyệt vời của Spring Boot. Vì container PostgreSQL sẽ được khởi động trên một cổng mạng ngẫu nhiên để tránh xung đột cổng trên máy dev, phương thức `configureProperties` sẽ lấy thông tin cổng và địa chỉ JDBC URL thực tế của container vừa chạy (`postgres::getJdbcUrl`) để **ghi đè động** các cấu hình kết nối database trong file `application.yml` của ứng dụng trước khi chạy test.
> * `userRepository.deleteAll()`: Thực hiện làm sạch dữ liệu bảng trong database PostgreSQL ảo trước khi bắt đầu chạy mỗi phương thức test (`@BeforeEach`), đảm bảo tính cô lập và độc lập dữ liệu tuyệt đối giữa các kịch bản test khác nhau, ngăn lỗi giao thoa dữ liệu.

## 5. Test Coverage & Best Practices

> **🔍 WHAT:** Code coverage là % dòng/branch code được thực thi bởi test. Jacoco là tool đo coverage cho Java, tích hợp với Maven/Gradle và có thể enforce minimum threshold.
>
> **💡 WHY:** Coverage cao không đảm bảo test tốt, nhưng coverage thấp chắc chắn có nhiều code chưa được test. Đặt minimum threshold (80%) trong CI để ngăn merge code không có test.
>
> **⚙️ HOW:** Đặt tên test theo pattern `methodName_stateUnderTest_expectedBehavior`. Dùng `given/when/then` structure (AAA: Arrange/Act/Assert). Mỗi test chỉ assert 1 behavior. Test cả happy path và error cases.
>
> **📍 WHEN/WHERE:** Chạy `mvn test jacoco:report` sau mỗi feature hoàn thành. CI pipeline fail nếu coverage dưới threshold. Report HTML ở `target/site/jacoco/index.html`.

```yaml
# application-test.yml – cấu hình riêng cho test
spring:
  datasource:
    url: jdbc:h2:mem:testdb
    driver-class-name: org.h2.Driver
  jpa:
    database-platform: org.hibernate.dialect.H2Dialect
    hibernate:
      ddl-auto: create-drop
```

```java
// Tên test chuẩn: methodName_state_expected
void createUser_withExistingEmail_throwsEmailAlreadyExistsException() {}
void getUser_withInvalidId_throwsResourceNotFoundException() {}
void calculateTotal_withEmptyCart_returnsZero() {}
void login_withWrongPassword_throwsBadCredentialsException() {}
```

```xml
<!-- Jacoco – enforce 80% line coverage trong pom.xml -->
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <configuration>
        <rules>
            <rule>
                <limits>
                    <limit>
                        <counter>LINE</counter>
                        <value>COVEREDRATIO</value>
                        <minimum>0.80</minimum>
                    </limit>
                </limits>
            </rule>
        </rules>
    </configuration>
</plugin>
```

```bash
# Chạy test và xem report
mvn test jacoco:report
# Mở file report: target/site/jacoco/index.html
```

> **📝 Giải thích chi tiết cấu hình và lệnh:**
> * `jdbc:h2:mem:testdb`: Cấu hình sử dụng cơ sở dữ liệu in-memory **H2 Database** chạy trực tiếp trên RAM thay thế cho database thật trong kịch bản test nhanh. `ddl-auto: create-drop` chỉ thị tự động tạo bảng khi chạy test và tự động drop sạch bảng khi test kết thúc.
> * `jacoco-maven-plugin`: Plugin đo lường độ bao phủ kiểm thử (Test Coverage). Cấu hình `<minimum>0.80</minimum>` quy định luật nghiêm ngặt: Nếu độ phủ kiểm thử của toàn bộ dự án dưới **80% số dòng code**, quá trình build dự án bằng Maven (`mvn package`) sẽ bị ép buộc thất bại (Build Failure). Đây là tiêu chuẩn kiểm soát chất lượng phần mềm vàng của các doanh nghiệp lớn khi chạy CI/CD.
> * `mvn test jacoco:report`: Lệnh Maven thực thi chạy toàn bộ các file test trong hệ thống, sau đó sinh ra một tệp báo cáo thống kê trực quan dạng giao diện web (HTML) trong thư mục `target/ site/jacoco/`, giúp lập trình viên mở trình duyệt xem rõ ràng từng dòng code nào đã có test (màu xanh) và dòng nào chưa được viết test phủ qua (màu đỏ).
