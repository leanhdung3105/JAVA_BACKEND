# 13. Microservices

> **Mục tiêu:** Hiểu kiến trúc Microservices, triển khai với Spring Cloud và giao tiếp giữa các services.

---

## 1. Monolith vs Microservices

> **🔍 WHAT:** Monolith là ứng dụng đơn khối deploy một lần, chia sẻ chung database. Microservices là kiến trúc chia nhỏ thành nhiều service độc lập, mỗi service có database riêng, deploy và scale riêng.
>
> **💡 WHY:** Monolith đơn giản cho team nhỏ nhưng khó scale khi lớn – một tính năng đơn giản phải redeploy toàn bộ ứng dụng, một lỗi nhỏ có thể làm sập toàn hệ thống. Microservices giải quyết điều này nhưng thêm phức tạp về vận hành.
>
> **⚙️ HOW:** Phân chia theo Business Domain (User Service, Order Service, Product Service). Mỗi service là Spring Boot app độc lập, có DB riêng, giao tiếp qua HTTP (REST/gRPC) hoặc message queue. Service Discovery (Eureka) giúp tìm nhau tự động.
>
> **📍 WHEN/WHERE:** Bắt đầu với Monolith, chuyển sang Microservices khi: team > 10 người, release cycle bị chặn bởi nhau, cần scale độc lập. KHÔNG phải silver bullet – nhiều startup thành công với Monolith tốt.

```
Monolith                          Microservices
Monolith                          Microservices
┌──────────────────┐              ┌──────────┐ ┌──────────┐ ┌──────────┐
│  Single App      │              │  User    │ │  Order   │ │ Product  │
│  ┌────────────┐  │      vs      │ Service  │ │ Service  │ │ Service  │
│  │ Controller │  │              └────┬─────┘ └────┬─────┘ └────┬─────┘
│  │  Service   │  │                   │              │              │
│  │ Repository │  │              ┌────▼─────┐ ┌────▼─────┐ ┌────▼─────┐
│  │  Service   │  │                   │              │              │
│  │ Repository │  │              ┌────▼─────┐ ┌────▼─────┐ ┌────▼─────┐
│  └────────────┘  │              │  UserDB  │ │ OrderDB  │ │ProductDB │
│    Single DB     │              └──────────┘ └──────────┘ └──────────┘
└──────────────────┘
```

| | Monolith | Microservices |
|---|---------|---------------|
| **Deployment** | Đơn giản | Phức tạp |
| **Scale** | Scale toàn bộ | Scale độc lập |
| **Fault isolation** | Một lỗi sập cả app | Lỗi cô lập từng service |
| **Phù hợp** | Team nhỏ, app mới | Team lớn, domain phức tạp |

## 2. Spring Cloud Components

> **🔍 WHAT:** Spring Cloud là bộ tools xây dựng trên Spring Boot giải quyết các challenges của distributed systems: Service Discovery, API Gateway, Circuit Breaker, Distributed Config, Distributed Tracing.
>
> **💡 WHY:** Microservices tạo ra nhiều vấn đề mới: làm sao service tìm địa chỉ nhau (Discovery)? Làm sao route request đúng service (Gateway)? Làm sao handle khi một service down (Circuit Breaker)? Spring Cloud giải quyết từng vấn đề này.
>
> **⚙️ HOW:** Thêm Spring Cloud BOM vào pom.xml, thêm từng starter dependency cho từng component cần dùng. Các component làm việc cùng nhau trong ecosystem Spring Boot.
>
> **📍 WHEN/WHERE:** Khi chuyển từ Monolith sang Microservices. Không phải toàn bộ component đều cần – chỉ dùng những gì giải quyết vấn đề thực tế của dự án.

```
Clients
   ↓
API Gateway (Spring Cloud Gateway)  ← Single entry point, routing, auth
   ↓
Service Discovery (Eureka)          ← Service registry, load balancing
   ↑
User Service ──────────────────────── Config Server (Spring Cloud Config)
Order Service ─────────────────────── Distributed Tracing (Zipkin)
Product Service ───────────────────── Circuit Breaker (Resilience4j)
```

## 3. Service Discovery – Eureka

> **🔍 WHAT:** Eureka là Service Registry – nơi mỗi microservice đăng ký địa chỉ (IP:port) của mình. Các service khác hỏi Eureka để tìm địa chỉ thay vì hardcode IP – vì IP có thể thay đổi khi scale.
>
> **💡 WHY:** Trong môi trường dynamic (container, cloud), instance IP/port thay đổi liên tục khi deploy, scale up/down. Hardcode IP không thể scale. Eureka tự động cập nhật địa chỉ và heartbeat kiểm tra health.
>
> **⚙️ HOW:** Eureka Server chạy như service riêng. Mỗi microservice (Eureka Client) tự đăng ký khi startup với `@EnableDiscoveryClient`. Khi gọi service khác, dùng service name (`lb://user-service`) thay vì IP.
>
> **📍 WHEN/WHERE:** Bắt buộc khi có nhiều microservice giao tiếp với nhau. Trong Kubernetes môi trường production thường dùng Kubernetes DNS thay Eureka. Eureka phù hợp cho bare metal hoặc VM deployment.

```java
// Eureka Server
@SpringBootApplication
@EnableEurekaServer
public class DiscoveryServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(DiscoveryServerApplication.class, args);
    }
}

// application.yml của Eureka Server
server:
  port: 8761
eureka:
  client:
    register-with-eureka: false  # server không tự đăng ký làm client
    fetch-registry: false

// application.yml của mỗi Microservice (Eureka Client)
spring:
  application:
    name: user-service  # tên đăng ký định danh trong Eureka
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

> **📝 Giải thích chi tiết code Eureka Service Discovery:**
> * `@EnableEurekaServer`: Đánh dấu class entry point này chạy với vai trò là máy chủ **Eureka Service Registry**. Nó mở cổng 8761 để lắng nghe các client đăng ký.
> * `register-with-eureka: false` & `fetch-registry: false`: Vì đây là máy chủ Registry trung tâm (Eureka Server), cấu hình này chặn không cho nó tự đăng ký chính mình thành client và không cần tải thông tin Registry từ server khác.
> * `spring.application.name: user-service`: **Cực kỳ quan trọng**. Đặt tên định danh duy nhất cho microservice. Tên này sẽ được đăng ký lên Eureka để các microservice khác hoặc API Gateway sử dụng gọi kết nối (ví dụ: gọi tới `user-service` thay vì gọi IP cứng).
> * `defaultZone`: Địa chỉ trỏ tới Eureka Server trung tâm. Client định kỳ gửi các tín hiệu **Heartbeat** (nhịp đập kiểm tra sức khỏe) lên địa chỉ này để báo cho Server biết instance vẫn đang sống khỏe mạnh. Nếu quá mốc thời gian quy định Eureka không nhận được heartbeat, nó tự động xóa địa chỉ client đó khỏi registry để tránh lỗi gọi nhầm.

## 4. API Gateway – Spring Cloud Gateway

> **🔍 WHAT:** API Gateway là single entry point cho tất cả client requests – nhận request, authenticate, route đến đúng microservice, áp dụng cross-cutting concerns (rate limiting, logging, CORS).
>
> **💡 WHY:** Thay vì client biết địa chỉ từng microservice (phức tạp, insecure), API Gateway cung cấp 1 URL duy nhất. Tập trung authentication, rate limiting, SSL termination ở một nơi thay vì mỗi service tự làm.
>
> **⚙️ HOW:** Cấu hình routes trong `application.yml` – map URL path đến service name (qua Eureka). Filter có thể modify request/response, add headers, validate JWT trước khi forward. `lb://` prefix cho load balancing qua Eureka.
>
> **📍 WHEN/WHERE:** Bắt buộc trong kiến trúc Microservices production. Client (web app, mobile) chỉ biết Gateway URL. Tất cả request đều đi qua Gateway – đây là chokepoint cần monitoring cẩn thận.

```yaml
# application.yml của API Gateway
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service   # lb:// = load balanced qua Eureka
          predicates:
            - Path=/api/v1/users/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20

        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/v1/orders/**
```

```java
// JWT Global Filter trong Gateway
@Component
public class JwtAuthGatewayFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = extractToken(exchange.getRequest());
        if (isValid(token)) {
            // Truyền userId cho downstream service qua header
            exchange = exchange.mutate()
                .request(r -> r.header("X-User-Id", extractUserId(token)))
                .build();
            return chain.filter(exchange);
        }
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();
    }
}
```

> **📝 Giải thích chi tiết cấu hình API Gateway:**
> * `routes`: Danh sách các cấu hình định tuyến (Routing).
>   * `uri: lb://user-service`: Áp dụng cơ chế **Load Balancing (Cân bằng tải)** tích hợp. Ký tự `lb://` chỉ thị cho Gateway đi hỏi Eureka Server danh sách các IP đang chạy của `user-service`, sau đó tự động phân phối các request đều cho các IP đó xử lý (sử dụng thuật toán Round Robin mặc định).
>   * `predicates: - Path=/api/v1/users/**`: Bộ lọc điều kiện so khớp đường dẫn. Mọi request client gửi lên Gateway có chứa đường dẫn bắt đầu bằng `/api/v1/users/` sẽ được định tuyến gửi về cho `user-service`.
>   * `RequestRateLimiter` + `redis-rate-limiter`: Cấu hình giới hạn tần suất request (Rate Limiting) tập trung sử dụng Redis. `replenishRate: 10` cho phép trung bình 10 request/giây; `burstCapacity: 20` cho phép lượng request bùng nổ tối đa 20 request/giây trước khi chặn ném lỗi 429.
> * `GlobalFilter`: Bộ lọc toàn cục chạy cho mọi request đi qua Gateway:
>   * **Cơ chế xác thực JWT tập trung**: Trình lọc `JwtAuthGatewayFilter` sẽ đọc và kiểm tra tính hợp lệ của token JWT. Nếu hợp lệ, nó sẽ bóc tách `userId` từ token và tiêm trực tiếp vào Header của request (`X-User-Id`) trước khi chuyển tiếp (forward) request tới microservice đích (downstream). Nhờ đó, các microservice nội bộ hoàn toàn giải phóng khỏi code xử lý xác thực token rườm rà, chỉ cần lấy trực tiếp `X-User-Id` ở header để xử lý business logic!

## 5. Giao tiếp giữa Services

> **🔍 WHAT:** Services giao tiếp theo 2 cách: Synchronous (HTTP/gRPC – request-response) và Asynchronous (Message Queue – fire-and-forget). Mỗi cách có trade-off về coupling và complexity khác nhau.
>
> **💡 WHY:** Chọn đúng cách giao tiếp quyết định resilience của hệ thống. Synchronous coupling chặt hơn (nếu service B down, service A cũng fail). Asynchronous loose coupling nhưng eventual consistency phức tạp hơn.
>
> **⚙️ HOW:** OpenFeign là HTTP client declarative cho synchronous call – khai báo interface, Spring tạo implementation. RabbitMQ/Kafka cho async. Dùng Circuit Breaker bọc synchronous call để handle failure.
>
> **📍 WHEN/WHERE:** Synchronous: khi cần kết quả ngay để xử lý tiếp (check user tồn tại trước khi tạo order). Asynchronous: khi không cần kết quả ngay (gửi email sau khi đặt hàng, update analytics). Ưu tiên async khi có thể để tăng resilience.

```java
// OpenFeign – Synchronous HTTP call
@SpringBootApplication
@EnableFeignClients
public class OrderServiceApplication {}

@FeignClient(name = "user-service", path = "/api/v1/users")
public interface UserServiceClient {
    @GetMapping("/{id}")
    UserResponse getUserById(@PathVariable Long id);
}

@Service @RequiredArgsConstructor
public class OrderService {
    private final UserServiceClient userServiceClient;

    public OrderResponse createOrder(CreateOrderRequest request) {
        UserResponse user = userServiceClient.getUserById(request.getUserId());
        // ...
    }
}
```

> **📝 Giải thích chi tiết code giao tiếp:**
> * `@EnableFeignClients`: Kích hoạt bộ quét Feign Client của Spring Cloud.
> * `@FeignClient(name = "user-service", path = "/...")`:
>   * Khai báo một **Declarative HTTP Client**. Bạn chỉ cần tạo một Interface, viết chữ ký hàm dạng REST Controller (`@GetMapping`). Spring Boot sẽ tự động triển khai (implement) hoàn chỉnh toàn bộ mã nguồn gửi HTTP request, tự gọi tích hợp với Eureka để cân bằng tải và tự bóc tách JSON trả về thành đối tượng `UserResponse` một cách tự động, giúp việc gọi API giữa các service giống hệt như gọi một phương thức Java thông thường trong local project.

## 6. Circuit Breaker – Resilience4j

> **🔍 WHAT:** Circuit Breaker (cầu dao) là pattern xử lý failure trong distributed systems – khi service đích liên tục fail, "circuit breaker mở" và tự động từ chối gọi tới service đó (trả fallback ngay), thay vì chờ timeout.
>
> **💡 WHY:** Trong microservices, cascade failure là nguy hiểm – service A gọi B fail → timeout → thread pool đầy → A cũng chết → C gọi A cũng chết. Circuit Breaker ngắt chuỗi này, bảo vệ hệ thống khỏi failure lan rộng.
>
> **⚙️ HOW:** 3 trạng thái: CLOSED (bình thường), OPEN (đang fail – reject ngay, gọi fallback), HALF_OPEN (thử lại). Cấu hình: `failureRateThreshold` (% fail để mở), `waitDurationInOpenState` (chờ bao lâu trước khi thử lại).
>
> **📍 WHEN/WHERE:** Bọc tất cả synchronous service-to-service calls. Luôn cung cấp `fallbackMethod` – khi Circuit Breaker mở, trả dữ liệu cached, default value, hoặc partial response thay vì lỗi 500.

```yaml
resilience4j:
  circuitbreaker:
    instances:
      user-service:
        slidingWindowSize: 10
        failureRateThreshold: 50      # mở khi 50% request fail
        waitDurationInOpenState: 10s  # chờ 10s ở trạng thái OPEN rồi thử lại ở HALF_OPEN
        permittedNumberOfCallsInHalfOpenState: 3
  retry:
    instances:
      user-service:
        maxAttempts: 3
        waitDuration: 500ms
  timelimiter:
    instances:
      user-service:
        timeoutDuration: 3s           # timeout sau 3s
```

```java
@Service
public class OrderService {

    @CircuitBreaker(name = "user-service", fallbackMethod = "getUserFallback")
    @Retry(name = "user-service")
    @TimeLimiter(name = "user-service")
    public UserResponse getUser(Long userId) {
        return userServiceClient.getUserById(userId);
    }

    // Fallback – trả về khi circuit open hoặc timeout
    public UserResponse getUserFallback(Long userId, Exception e) {
        log.warn("User service unavailable for userId: {}", userId);
        return UserResponse.builder().id(userId).fullName("Unknown User").build();
    }
}
```

> **📝 Giải thích chi tiết code Circuit Breaker:**
> * `failureRateThreshold: 50`: Nếu trong 10 request gần nhất (`slidingWindowSize`), có từ 50% số request bị lỗi (hoặc timeout quá 3s), cầu dao sẽ lập tức chuyển sang trạng thái **OPEN**. Mọi request tiếp theo gọi tới `user-service` sẽ bị chặn đứng ngay lập tức tại đây mà không được phép gửi sang mạng thật, thay vào đó hệ thống tự động nhảy vào hàm `getUserFallback` xử lý. Giúp `user-service` có thời gian rảnh rỗi để tự hồi phục, tránh bị quá tải dồn dập request khi đang gặp sự cố.
> * `permittedNumberOfCallsInHalfOpenState: 3`: Sau 10 giây nằm ở trạng thái OPEN, cầu dao chuyển sang **HALF_OPEN** và cho phép thử nghiệm gửi 3 request thật. Nếu cả 3 đều thành công, cầu dao tự động đóng lại (**CLOSED**) để hoạt động bình thường. Nếu có lỗi, nó quay về trạng thái **OPEN** tiếp.
> * `@Retry`: Tích hợp tính năng tự động thử lại tối đa 3 lần, mỗi lần cách nhau 500ms trước khi thực sự coi request đó là thất bại. Rất hữu ích khi mạng bị chập chờn nhất thời (Transient Faults).
> * `@TimeLimiter(timeoutDuration: 3s)`: Cấu hình giới hạn thời gian chờ. Nếu API gọi quá 3 giây không có phản hồi, Spring sẽ tự ép buộc coi request đó bị Timeout lỗi để tránh việc giữ luồng (thread) chờ quá lâu làm cạn kiệt tài nguyên hệ thống.
> * `getUserFallback`: Phương thức xử lý thay thế khi hệ thống gặp lỗi hoặc cầu dao đang mở. Bắt buộc phải có chữ ký hàm (tham số và kiểu trả về) giống hệt với phương thức chính, đính kèm thêm tham số Exception nhận thông tin lỗi. Ở đây ta trả về một User mặc định là `"Unknown User"` giúp API đặt hàng vẫn hoàn tất được thay vì ném lỗi 500 sập toàn bộ flow của khách hàng.

## 7. Distributed Tracing – Zipkin

> **🔍 WHAT:** Distributed Tracing là cơ chế theo dõi một request khi nó đi qua nhiều microservices – tạo Trace ID duy nhất và ghi lại thời gian tại mỗi service (Span).
>
> **💡 WHY:** Khi có lỗi hoặc chậm trong Microservices, rất khó debug vì request đi qua nhiều service. Zipkin UI cho phép xem toàn bộ journey của request, biết service nào chậm, ở đâu có lỗi.
>
> **⚙️ HOW:** Micrometer Tracing tự động inject Trace ID vào log và HTTP header khi request được forward giữa services. Zipkin collector nhận và lưu trace data. Zipkin UI visualize service dependency graph và trace timeline.
>
> **📍 WHEN/WHERE:** Bật trong mọi microservice môi trường dev/staging với sampling 100%. Production dùng sampling 1-10% để tránh overhead. Khi debug performance issue, tăng sampling tạm thời.

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>
```

```yaml
management:
  tracing:
    sampling:
      probability: 1.0  # trace 100% request (production: 0.1)
spring:
  zipkin:
    base-url: http://localhost:9411
```

```bash
# Khởi chạy Zipkin Server cực nhanh bằng Docker
docker run -d -p 9411:9411 openzipkin/zipkin
```

> **📝 Giải thích chi tiết cấu hình Distributed Tracing:**
> * `micrometer-tracing`: Công cụ tự động tạo **Trace ID** duy nhất khi request đi vào API Gateway, tự động tiêm ID này vào Header của HTTP request truyền qua Feign Client và tự động ghi Trace ID này vào mọi dòng Log ghi nhận của toàn bộ microservices liên quan.
> * `sampling.probability: 1.0`: Tỷ lệ lấy mẫu ghi vết. Giá trị `1.0` chỉ định ghi vết toàn bộ 100% số request gửi lên hệ thống (phù hợp khi dev). Lên Production ta nên đặt `0.1` (10%) để tránh overhead ghi nhận đĩa cứng và băng thông mạng quá nhiều.
> * `http://localhost:9411`: Địa chỉ UI của Zipkin. Truy cập giao diện này, lập trình viên chỉ cần gõ Trace ID lấy từ log là có thể quan sát được dòng thời gian (timeline) chi tiết dạng biểu đồ Gantt: request xử lý tại Gateway mất bao nhiêu ms, gọi sang User Service mất bao nhiêu ms, query DB mất bao nhiêu ms, giúp khoanh vùng và tối ưu các "điểm nghẽn" hiệu năng (Performance Bottlenecks) cực kỳ dễ dàng.

## 8. Centralized Configuration (Spring Cloud Config)

> **🔍 WHAT:** Spring Cloud Config Server là service tập trung quản lý cấu hình cho tất cả microservices – config được lưu trong Git repository và được phân phối đến từng service khi startup.
>
> **💡 WHY:** 10 microservice có 10 file config riêng – thay đổi DB URL phải sửa 10 nơi. Config Server tập trung ở 1 nơi, mỗi service pull config về. Thay đổi config không cần redeploy service (dynamic refresh với `@RefreshScope`).
>
> **⚙️ HOW:** Config Server đọc config từ Git repo (branch, label tương ứng với environment). Client service cấu hình `spring.config.import=configserver:http://config-server:8888`. Sensitive values nên encrypt.
>
> **📍 WHEN/WHERE:** Khi có nhiều microservice cần quản lý config đồng bộ. Phổ biến trong enterprise. Có thể dùng Kubernetes ConfigMap/Secret làm alternative trong K8s environment.

```yaml
# Config Server application.yml
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/myorg/config-repo
          default-label: main

# Client service bootstrap.yml
spring:
  config:
    import: configserver:http://localhost:8888
  application:
    name: user-service
  profiles:
    active: dev
```

> **📝 Giải thích chi tiết cấu hình Config Server:**
> * `config/server/git/uri`: Chỉ định đường dẫn tới kho lưu trữ Git chứa toàn bộ các file cấu hình `.properties` hoặc `.yml` của hệ thống.
> * `spring.config.import`: Cấu hình ở phía Client (các microservice). Khi khởi động, các service sẽ bỏ qua file cấu hình local và gửi yêu cầu kết nối tới Config Server cổng `8888`. Dựa trên tên ứng dụng (`user-service`) và môi trường (`dev`), Config Server sẽ tự động tìm kiếm file tương ứng là `user-service-dev.yml` trong kho Git để tải về cấu hình nạp vào ứng dụng. Giúp quản lý cấu hình toàn hệ thống tại một nơi duy nhất vô cùng an toàn và thuận tiện.
