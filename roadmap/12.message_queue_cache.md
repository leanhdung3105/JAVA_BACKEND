# 12. Message Queue & Cache

> **Mục tiêu:** Sử dụng Redis làm cache và RabbitMQ/Kafka làm message broker để tăng hiệu suất hệ thống.

---

## 1. Redis Cache

> **🔍 WHAT:** Redis là in-memory data store cực nhanh, dùng làm cache (lưu kết quả query tốn kém), session store, rate limiter, leaderboard, pub/sub. Spring Boot tích hợp qua `spring-boot-starter-data-redis`.
>
> **💡 WHY:** Query DB tốn 10-100ms, đọc Redis tốn <1ms. Caching giảm đáng kể load DB và tăng throughput API. Dữ liệu ít thay đổi (danh mục sản phẩm, profile user) phù hợp để cache.
>
> **⚙️ HOW:** Spring Cache abstraction với `@Cacheable`, `@CacheEvict`, `@CachePut` annotations – cache logic trong code. Hoặc dùng `RedisTemplate` trực tiếp cho advanced use case (sorted set, pub/sub, distributed lock).
>
> **📍 WHEN/WHERE:** Cache dữ liệu read-heavy ít thay đổi: danh sách category, thông tin product, user profile. Không cache dữ liệu nhạy cảm (password) hay dữ liệu real-time (stock price). TTL (time-to-live) phải phù hợp với tần suất thay đổi data.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
```

```java
@Configuration
@EnableCaching
public class RedisConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .serializeKeysWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()))
            .disableCachingNullValues();

        return RedisCacheManager.builder(factory)
            .cacheDefaults(config)
            .withCacheConfiguration("products", config.entryTtl(Duration.ofHours(1)))
            .withCacheConfiguration("users", config.entryTtl(Duration.ofMinutes(5)))
            .build();
    }
}

@Service @RequiredArgsConstructor
public class ProductService {

    @Cacheable(value = "products", key = "#id")
    public ProductResponse getProductById(Long id) {
        // Chỉ chạy khi cache miss – cache hit trả về từ Redis
        return productRepository.findById(id).map(this::toResponse).orElseThrow();
    }

    @CacheEvict(value = "products", key = "#id")  // xóa cache khi update
    public ProductResponse updateProduct(Long id, UpdateProductRequest request) { /* ... */ }

    @CacheEvict(value = "products", allEntries = true)  // xóa toàn bộ cache
    public void clearProductCache() {}
}
```

> **📝 Giải thích chi tiết code Redis Caching:**
> * `@EnableCaching`: Annotation kích hoạt tính năng trừu tượng hóa bộ nhớ đệm (Cache Abstraction) của Spring Boot.
> * `CacheManager`: Bộ quản lý cache. Ở đây ta khởi tạo `RedisCacheManager` để chỉ định sử dụng Redis làm công cụ lưu trữ cache vật lý.
> * `entryTtl(Duration.ofMinutes(10))`: Thiết lập **TTL (Time To Live - Thời gian sống)** mặc định cho dữ liệu cache là 10 phút. Quá thời gian này, dữ liệu tự biến mất khỏi Redis để buộc ứng dụng phải truy vấn lại dữ liệu mới từ DB, tránh lỗi "dữ liệu cũ bị treo" (stale data).
> * `StringRedisSerializer` / `GenericJackson2JsonRedisSerializer`:
>   * `StringRedisSerializer`: Mã hóa các Key cache của Redis ở dạng chuỗi String thuần dễ đọc (ví dụ: `products::42`).
>   * `GenericJackson2JsonRedisSerializer`: Tự động chuyển đổi đối tượng Java Response DTO thành chuỗi **JSON** trước khi lưu xuống Redis. Giúp ta dễ dàng mở Redis lên đọc dữ liệu để debug, đồng thời các hệ thống viết bằng ngôn ngữ khác (như Node.js, Python) cũng có thể đọc hiểu chung vùng cache này.
> * `.withCacheConfiguration("products", ...)`: Cấu hình thời gian sống TTL chuyên biệt cho từng vùng dữ liệu khác nhau (ví dụ: dữ liệu sản phẩm ít thay đổi nên cache hẳn 1 giờ, dữ liệu user hay đổi nên chỉ cache 5 phút).
> * `@Cacheable(value = "products", key = "#id")`:
>   * **Cơ chế hoạt động**: Khi API được gọi, Spring sẽ tự động tìm kiếm trong Redis xem có key `products::[id]` hay chưa. Nếu đã có (**Cache Hit**), Spring lấy dữ liệu trong Redis chuyển đổi ngược lại DTO và trả về ngay lập tức, phương thức Java hoàn toàn không được thực thi. Nếu chưa có (**Cache Miss**), Spring mới chạy code bên trong hàm để truy vấn DB thật, sau đó tự động lưu kết quả trả về vào Redis rồi phản hồi cho user.
> * `@CacheEvict(value = "products", key = "#id")`:
>   * **Giải quyết vấn đề nhất quán dữ liệu**: Khi bạn thực hiện sửa đổi dữ liệu sản phẩm, ta bắt buộc phải xóa bản cache cũ tương ứng trong Redis đi. Cờ `allEntries = true` sẽ xóa toàn bộ mọi cache sản phẩm hiện có trong vùng `products`.

### Redis Template trực tiếp

```java
@Service @RequiredArgsConstructor
public class SessionService {
    private final RedisTemplate<String, Object> redisTemplate;

    public void saveSession(String userId, Object data) {
        redisTemplate.opsForValue().set("session:" + userId, data, Duration.ofHours(24));
    }

    // Rate limiting
    public boolean isRateLimited(String ip) {
        Long count = redisTemplate.opsForValue().increment("ratelimit:" + ip);
        if (count == 1) redisTemplate.expire("ratelimit:" + ip, Duration.ofMinutes(1));
        return count > 100; // max 100 req/phút
    }
}
```

> **📝 Giải thích chi tiết code:**
> * `RedisTemplate<String, Object>`: Lớp helper cấp thấp của Spring giúp thao tác trực tiếp với toàn bộ các cấu hình và cấu trúc dữ liệu nguyên bản của Redis (String, Hash, List, Set, Sorted Set) một cách linh hoạt, vượt trội hơn các Annotation tự động.
> * `opsForValue().set(...)`: Sử dụng cấu trúc dữ liệu String cơ bản của Redis để gán cặp Key-Value kèm theo thời gian sống (TTL) hết hạn sau 24 giờ.
> * `opsForValue().increment(...)`: Phương thức thực hiện phép cộng `INCR` trong Redis. Điểm cực mạnh là phép toán này thực thi **nguyên tử (Atomic)** hoàn toàn trên Redis, giúp đếm chính xác số lượng request từ một địa chỉ IP gửi lên trong môi trường đa luồng cực nhanh mà không bị lỗi tranh chấp dữ liệu (Race Condition).
> * `redisTemplate.expire(...)`: Thiết lập thời gian sống cho bộ đếm giới hạn tần suất (Rate Limiting) tự động biến mất sau 1 phút. Nếu số lần đếm vượt quá 100 lần trong 1 phút, hệ thống sẽ trả về `true` để chặn request từ IP đó.

## 2. RabbitMQ

> **🔍 WHAT:** RabbitMQ là message broker implementing AMQP protocol – cho phép gửi message giữa các service qua Exchange và Queue. Producer gửi message, Consumer nhận và xử lý bất đồng bộ.
>
> **💡 WHY:** Tách biệt Producer và Consumer – khi đặt hàng, OrderService không cần chờ EmailService gửi email xong. Nếu EmailService down, message vẫn nằm trong Queue và sẽ được xử lý khi service khôi phục. Tăng resilience và throughput.
>
> **⚙️ HOW:** Exchange nhận message và route đến Queue theo routing key (Topic Exchange) hoặc broadcast (Fanout). Consumer `@RabbitListener` poll Queue và xử lý. Dead Letter Queue (DLQ) nhận message xử lý thất bại để retry sau.
>
> **📍 WHEN/WHERE:** Gửi email/SMS sau transaction; xử lý file upload bất đồng bộ; notify các service khác khi có event; decouple service trong microservices. Phù hợp cho task queue và event notification.

```java
@Configuration
public class RabbitMQConfig {
    public static final String ORDER_EXCHANGE = "order.exchange";
    public static final String ORDER_CREATED_QUEUE = "order.created";
    public static final String ORDER_CREATED_KEY = "order.created";

    @Bean
    public TopicExchange orderExchange() {
        return new TopicExchange(ORDER_EXCHANGE, true, false);
    }

    @Bean
    public Queue orderCreatedQueue() {
        return QueueBuilder.durable(ORDER_CREATED_QUEUE)
            .withArgument("x-dead-letter-exchange", "dead.letter.exchange") // DLQ
            .build();
    }

    @Bean
    public Binding orderCreatedBinding() {
        return BindingBuilder.bind(orderCreatedQueue())
            .to(orderExchange()).with(ORDER_CREATED_KEY);
    }

    @Bean
    public MessageConverter jsonMessageConverter() {
        return new Jackson2JsonMessageConverter();
    }
}

// Publisher
@Service @RequiredArgsConstructor
public class OrderService {
    private final RabbitTemplate rabbitTemplate;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = orderRepository.save(buildOrder(request));
        // Publish event – không block, không chờ email gửi xong
        rabbitTemplate.convertAndSend(
            RabbitMQConfig.ORDER_EXCHANGE,
            RabbitMQConfig.ORDER_CREATED_KEY,
            new OrderCreatedEvent(order.getId(), order.getUserId(), order.getTotal())
        );
        return order;
    }
}

// Consumer
@Component @Slf4j @RequiredArgsConstructor
public class OrderEventConsumer {
    private final EmailService emailService;

    @RabbitListener(queues = RabbitMQConfig.ORDER_CREATED_QUEUE)
    public void handleOrderCreated(OrderCreatedEvent event) {
        log.info("Processing order: {}", event.getOrderId());
        try {
            emailService.sendOrderConfirmation(event);
        } catch (Exception e) {
            log.error("Failed to process order {}: {}", event.getOrderId(), e.getMessage());
            throw new AmqpRejectAndDontRequeueException(e); // gửi sang DLQ
        }
    }
}
```

> **📝 Giải thích chi tiết code RabbitMQ:**
> * `TopicExchange`: Bộ định tuyến tin nhắn dạng Topic. Nó nhận tin nhắn từ Producer và dựa trên mã định tuyến **Routing Key** (ví dụ: `order.created`) để gửi chính xác tin nhắn tới các Queue tương ứng. Cấu hình `true, false` chỉ định Exchange bền vững (Durable) - không bị mất cấu hình khi restart RabbitMQ Server.
> * `QueueBuilder.durable(...)`: Tạo một hàng đợi (Queue) lưu trữ tin nhắn bền vững (dữ liệu tin nhắn ghi xuống đĩa cứng).
> * `x-dead-letter-exchange`: Cấu hình **Dead Letter Exchange (DLX)**. Khi tin nhắn đi vào Queue này và bị lỗi xử lý (Consumer ném lỗi ngoại lệ), thay vì bị mất vĩnh viễn hoặc bị kẹt lặp đi lặp lại vô hạn, RabbitMQ sẽ tự động chuyển tin nhắn lỗi này sang một Exchange phụ (DLX) để gom vào hàng đợi lỗi riêng để các lập trình viên hoặc công cụ tự động xử lý/retry sau.
> * `BindingBuilder.bind(...)`: Tạo liên kết giữa Exchange và Queue thông qua mã khóa Routing Key tương ứng.
> * `Jackson2JsonMessageConverter`: Cấu hình tự động chuyển đổi các Event Object của Java thành chuỗi JSON khi gửi và tự động giải mã JSON ngược lại thành đối tượng Java khi nhận tin nhắn, thay vì mã hóa nhị phân Java thuần túy.
> * `rabbitTemplate.convertAndSend(...)`: Phương thức gửi tin nhắn bất đồng bộ của Spring. Lệnh này gửi tin nhắn lên Exchange và kết thúc ngay lập tức chỉ trong khoảng vài Microseconds, giải phóng luồng chính cho Client mà không cần đợi gửi email xong.
> * `@RabbitListener`: Annotation chỉ thị cho Spring Boot liên tục lắng nghe (poll) tin nhắn từ hàng đợi `order.created`. Mỗi khi có tin nhắn mới đi vào Queue, Spring tự động kích hoạt phương thức `handleOrderCreated` xử lý bất đồng bộ.
> * `AmqpRejectAndDontRequeueException`: Ngoại lệ đặc biệt. Khi ném lỗi này, RabbitMQ hiểu tin nhắn bị lỗi nặng và **không được phép xếp hàng lại (requeue)** vào queue chính (tránh việc loop lỗi liên tục gây treo hệ thống), mà đưa thẳng sang hàng đợi lỗi DLQ đã cấu hình.

## 3. Apache Kafka (giới thiệu)

> **🔍 WHAT:** Apache Kafka là distributed event streaming platform – lưu events như log file bất biến (append-only), consumer có thể đọc lại từ bất kỳ offset nào, hỗ trợ millions of events/second.
>
> **💡 WHY:** Khác RabbitMQ (message broker, xóa khi consumed), Kafka lưu events vĩnh viễn – consumer mới có thể replay toàn bộ lịch sử. Phù hợp cho event sourcing, real-time analytics, audit log, data pipeline.
>
> **⚙️ HOW:** Producer gửi message vào Topic chia thành Partitions. Consumer Group đọc từ partition, offset tracking đảm bảo mỗi message được xử lý đúng 1 lần. Spring Kafka tích hợp qua `@KafkaListener`.
>
> **📍 WHEN/WHERE:** Hệ thống lớn cần high-throughput event streaming (>100k events/s); audit trail cần replay; real-time analytics pipeline; microservices event sourcing. Kafka phức tạp hơn RabbitMQ – chỉ dùng khi thực sự cần.

```java
// Producer
@Service @RequiredArgsConstructor
public class KafkaProducer {
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public void sendOrderEvent(String orderId, OrderCreatedEvent event) {
        kafkaTemplate.send("orders", orderId, event); // key = orderId để đảm bảo ordering
    }
}

// Consumer
@Component @Slf4j
public class KafkaConsumer {
    @KafkaListener(topics = "orders", groupId = "order-processor")
    public void consume(OrderCreatedEvent event) {
        log.info("Processing order from Kafka: {}", event.getOrderId());
        // xử lý event
    }
}
```

> **📝 Giải thích chi tiết code Kafka:**
> * `kafkaTemplate.send("orders", orderId, event)`: Gửi sự kiện vào Topic có tên là `"orders"`. 
>   * `orderId` đóng vai trò là **Message Key**. Kafka sử dụng thuật toán băm khóa để đảm bảo toàn bộ các tin nhắn có cùng một khóa `orderId` **luôn luôn được ghi vào cùng một Partition duy nhất**. Điều này đảm bảo tuyệt đối thứ tự tuần tự trước/sau của các sự kiện liên quan tới đơn hàng đó khi Consumer đọc xử lý (Message Ordering).
> * `@KafkaListener(topics = "orders", groupId = "order-processor")`: Lắng nghe sự kiện từ Topic `"orders"`. Cấu hình `groupId` giúp định danh nhóm xử lý. Kafka sẽ tự động cân bằng tải phân chia các partition của Topic cho các Consumer trong cùng nhóm để xử lý song song đạt hiệu suất cực cao.

## 4. Khi nào dùng gì?

> **🔍 WHAT:** Redis, RabbitMQ và Kafka đều là middleware, nhưng mỗi loại giải quyết vấn đề khác nhau – chọn đúng tool cho đúng use case quan trọng hơn là dùng tool "phổ biến nhất".
>
> **💡 WHY:** Dùng sai tool dẫn đến over-engineering (Kafka cho task queue đơn giản) hoặc thiếu tính năng (RabbitMQ cho event sourcing cần replay). Hiểu trade-off giúp ra quyết định đúng khi thiết kế.
>
> **⚙️ HOW:** Redis khi cần caching và tốc độ; RabbitMQ khi cần task queue đơn giản và reliability; Kafka khi cần event streaming, high throughput, hoặc message replay. Có thể kết hợp cả 3 trong 1 hệ thống.
>
> **📍 WHEN/WHERE:** Câu hỏi quan trọng: Có cần replay message không? (Kafka). Có cần routing phức tạp? (RabbitMQ). Chỉ cần cache kết quả? (Redis). Priority queue? (RabbitMQ). Real-time analytics? (Kafka).

| | Redis | RabbitMQ | Kafka |
|---|-------|----------|-------|
| **Use case chính** | Cache, session, rate limit | Task queue, async notification | Event streaming, log, analytics |
| **Throughput** | Rất cao | Cao | Rất cao (millions/s) |
| **Message persistence** | Optional | Có (disk) | Có (log-based, lâu dài) |
| **Message replay** | ❌ | ❌ | ✅ (bất kỳ offset nào) |
| **Ordering** | N/A | Per queue | Per partition |
| **Complexity** | Thấp | Trung bình | Cao |
| **Phù hợp** | Mọi dự án | Dự án vừa | Hệ thống lớn |
